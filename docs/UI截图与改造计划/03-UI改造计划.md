## 2. 设计决策：方案三（活动栏 → Obsidian 式侧栏视图切换器）

### 2.1 问题回顾

当前左侧有**两条功能重复的图标列**（dump 实测）：

| 元素 | 实测 bounds | 宽度 | 内容 |
|---|---|---|---|
| Ribbon（自研） | x 0–46vp | ≈44vp | 侧栏开关 / 搜索 / 图谱 / 白板 / 闪卡 / 命令面板 / 主题 / 调色板 |
| 活动栏（O5 新增） | x 46–90vp | ≈44vp | 新建 / Journal / AllPages / Graph / Flashcards / Whiteboards / Pdf（+ 底部 收藏/仓库/设置） |
| 内容面板 | x 90–306vp | **216vp** | 文件树 / 收藏 / 最近 |
| 主内容区 | x 306–1440vp | 1134vp | Tab 条 36vp + 内容 |

→ 两条图标列共占 90vp，却把真正的信息面板压到 216vp（Obsidian 为 240–260px），且 Graph/Whiteboards/Flashcards 在两列中**重复出现**。

### 2.2 方案三定案内容

**保留 Ribbon（44vp）作为唯一图标条，把 O5 活动栏改造为「侧栏视图切换器」——即 Obsidian 侧栏顶部的那一行视图标签，而不是第二条图标列。**

具体规格：

| 项 | 现状 | 改造后 | 理由 |
|---|---|---|---|
| 图标列数量 | 2 条（Ribbon + 活动栏） | **1 条**（Ribbon） | 对齐 Obsidian `Laptop(1)(3)(14)`：只有一条 ≈44px 图标条 |
| 视图切换器位置 | 无 | **侧栏面板顶部一行**（图标+文字的紧凑 chip，或纯图标 28vp 行） | Obsidian 侧栏顶部即「文件列表 ▾ / 搜索 / 书签」切换器 |
| 视图集合 | — | **文件（树）/ 搜索 / 书签 / 标签**（4 个语义） | Obsidian 侧栏的三个核心视图 + 标签；图谱/白板等**移出侧栏**（它们是主区页面，不是侧栏视图） |
| 侧栏面板宽度 | 216vp | **248vp**（范围 240–260vp） | 补齐被第二条图标列吃掉的空间；仍满足 40vp 热区与文件树缩进 |
| 侧栏顶部操作行 | 无 | 新建文件 / 新建文件夹 / 排序 / 折叠全部（28vp 行，图标 16vp） | 对齐 `Laptop(2)(3)` 的文件列表操作行 |
| 主导航去处 | 活动栏图标 | **保留在 Ribbon**（Journal/AllPages/Graph/Flashcards/Whiteboards/Pdf 已在其上）或收敛进命令面板 | Journal 与 AllPages 在 Ribbon 中已有入口；避免重复 |
| 设置/仓库入口 | 活动栏底部 | 保留 Ribbon 底部（设置齿轮 + 仓库切换） | 与 Obsidian 底部署位一致 |

> **执行状态（2026-09-25，W1 已落地并通过设备验证）**
> - ✅ 步骤 1：面板顶部**视图切换器**已上线 —— 四个 chip「文件 / 搜索 / 书签 / 标签」，状态存 `LeftSidebar.@State sidebarView`；标签视图数据源 `WorkspaceService.getAllTags()`。
> - ✅ 步骤 2：**44vp 活动栏图标列已下线**（`LeftSidebar` 中该 `Column` 整体移除，非隐藏）；侧栏总宽仍为 `SIDEBAR_DEFAULT = 260vp`，故面板由 **216vp → 约 266vp**（实测：面板 x 90→622px，即 45→311vp），落在 Obsidian 240–260px 区间上沿。
> - ✅ 步骤 3：活动栏独有入口已收敛到 Ribbon（`Ribbon.ets` 新增 `items[6..9]`：新建 `newFile` / Journal / AllPages / Pdf）；「收藏折叠」由区段标题自带折叠承担（原活动栏 star 图标冗余），「仓库切换」移入面板顶部操作行。
> - **实测证据**：`01-应用截图/W1-01-sidebar-files.jpeg`（左侧只剩一条图标列、面板变宽、顶部四 chip 齐全）、`W1-02-sidebar-tags.jpeg`（标签视图）。

### 3.6 图谱（30）
- ~~**P0：画布空白**~~ → **✅ 已修复并设备验收（2026-09-25，W1 提前完成）**
  - **根因（两条叠加）**：① `GraphView.ets` 中 `private ctx: CanvasRenderingContext2D | undefined;` **声明后从未实例化** → `Canvas(this.ctx)` 收到 `undefined` 不渲染，且 `drawGraph()` 开头的 `if (!this.ctx) return;` **每次都提前返回**；② `canvasWidth/canvasHeight` 恒为默认 800×600，从未随画布实测尺寸更新（平板实际 1130×679vp）→ 即使绘制也会 `clearRect` 不全、布局不居中。
  - **修复**：① `ctx` 改为 `new CanvasRenderingContext2D(this.settings)` 实例化；② Canvas 增加 `.onAreaChange()` 同步实测尺寸并**重建布局**（`GraphLayout.build(pages, w, h)` 以画布尺寸决定初始散布与斥力中心，故尺寸变化需重排而非仅重绘）。

### 3.7 侧栏信息架构（原判定已纠正 + 新发现的 P1，修复完成）

**① 纠正：原两条判定有误，已撤回（2026-09-25 设备对账）**
- 「同名页面重复出现」—— **设计如此**：「最近」列表与「文件树」两处出现同一页面，与 Obsidian 的 recent files + 文件列表一致，不是重复渲染。
- 「计数与实际不符」—— **计数是对的**：侧栏「N 个文件」= 已加载页面数，与树中条目数吻合（实测 3 = 3；修复后 8 = 8）。对账依据：日志 `[DataStore] Graph loaded. Pages: 3` 与树中「3 个文件」一致。
- 误判原因：把「最近」区的行数当成了文件树行数去和计数比。

**② 真缺陷（P1，已修复并设备验收）：空文件被静默丢弃 → 页面从文件树消失**
- 现象：`未命名 4.md`（内容仅 `- ` 空块）、`未命名 5.md`、**当天的 `2026-09-25.md`**（0 字节）三者均未出现在文件树；日志仅一句 `Empty or unreadable file`。
- 风险：结合 §3.11 记录的「整页被清空」缺陷（已修），一次意外清空即等于页面**永久从应用中消失** —— 文件还在磁盘，但树里没有、用户无从察觉与恢复。
- 根因：`DataStore.loadPageFromFile` 对 `readTextSync` 返回的空串**一律 return 跳过**；而 `readTextSync` 会把**读取异常也吞成空串**，所以不能无差别地建空页面（否则读失败会被后续保存写成 0 字节 → 真数据丢失）。
- 修复：新增 `FileRepository.hasContent(path)`（`statSync().size > 0`）区分两种情况 —— **仅当确属空文件**时按空页面加载；读取失败仍跳过并告警。
- **证据**：日志 `Empty file, loaded as empty page: …` ×5 + **`Graph loaded. Pages: 8`**（修复前 3）；侧栏显示「**8 个文件，0 个文件夹**」，与磁盘 8 个 .md 文件一致；截图 `01-应用截图/zz-侧栏空文件保留验证.jpeg`。

**③ 仍待做（W1 范围）**：侧栏顶部视图切换器（文件/搜索/书签/标签）、面板 216 → 248vp、顶部操作行 —— 见 §2.2。

**五条方法学教训（都付了代价换来的，务必沿用）**：
1. **测量前必须目视确认目标**——S-1 纠缠五轮（dump 字段不可靠 → 跨会话坐标 → 文字节点当容器 → 误判 builder → 红探针 0 像素），最后一次 `read_image` 目视即终结。**先看，再测。**
2. **dump 的 `attributes` 不含 fontSize / fontColor，`backgroundColor` 在部分节点也不可靠**；字号与配色结论必须走截图像素实测（连通域测 ink + 众数取色）。
3. **文本节点边界 ≠ 容器边界**：`find_node.py <文本> --bounds` 给的是文字节点；测容器背景/内边距必须先用几何筛选（宽高 + y 区间）定位容器。
4. **不要用 PowerShell here-string 直接做源码替换**：它的行尾是 CRLF，而本仓库文件有的 LF 有的 CRLF，行尾不一致会让替换**静默落空**；必须显式归一化，且替换后立即用 grep 确认命中。

- 官方六特性对照：通透材质 / 渐变模糊 / 按压弹性反馈 / 按压点光源 / 材质流光 / 智能反色。

### 4.2 三条**实测硬约束**（决定改造路径，不可绕过）
| # | 约束 | 实测证据 |
|---|---|---|
| 1 | `systemMaterial` **仅在 `Navigation`/`NavDestination` 标题栏，或横向 `Tabs` 的 `barPosition: End` 底部 TabBar 生效**；在普通组件上调用 → **THREAD_BLOCK_6S** | 主线程 `COStub_GrowElementsCapacityStwCopy`，utime≈1224（≈12s CPU） |
| 2 | `module.json5` 加 `metadata = enable`（应用级默认开启系统材质）→ **首次启动 appfreeze，后续启动反复退出** | 已回退移除 |
| 3 | 简单用 `Navigation` 包裹现有外壳 → **布局回归**（titleBar 独立布局模型，TabBar 被挤入内容区） | 上轮实测 |

→ 结论：**沉浸光感只能走「外壳迁移」路径**，且必须分步、每步实机回归。

### 4.3 阶段二落地设计（GL-2 → GL-5）

| 阶段 | 内容 | 关键实现 | 验收 |
|---|---|---|---|
| **GL-2 主壳迁移**（风险最高） | `MainContainer` → `Navigation` + `NavPathStack`；Home/Journal/Graph/Whiteboards/Flashcards/Pdf/Settings 改为 `NavDestination`；TabBar 保留为 Navigation 自定义 title 区（`titleMode(Free)` + 显式高度）；分屏 ContentPanes 置于内容区 | ① `titleMode(NavigationTitleMode.Free)` + 自定义 padding 显式控高（**不要依赖 titleBar 默认布局**）；② 先迁 **1 个页面**（Settings，最少依赖）→ 实机比对 → 再逐个迁；③ 返回键/深链回归清单 | 每迁一页：布局无回归（与 `01-应用截图/` 逐张比对） + 无 THREAD_BLOCK |
| **GL-3 标题栏材质** | TabBar 所在 titleBar 启用 `systemMaterial: ImmersiveMaterial(ADAPTIVE)` + `barStyle(STACK)`；内容区滚动联动 `scrollEffectOptions(GRADIENT_BLUR)` + `bindToScrollable` | 材质档位取 `MaterialTokens` 的语义角色（标题栏 = THIN）；`applyShadow` 默认 true 会**覆盖** `shadow()` → 标题栏现有 `shadow({radius})` 需改走 Token 的 `shadowRadius` | 标题栏随滚动渐变模糊；明/暗自适应；与系统 Dialog/Toast 材质并置不割裂 |
| **GL-4 底部导航材质** | 移动端胶囊栏：**先评估** `Tabs(barPosition: End) + barOverlap + systemMaterial` 迁移成本；≤3 天则走原生（材质/模糊全托管），否则保留自绘 + 仅接光效 | 决策规则沿用 v2 §六第 5 条（GL-4 开始前 48h 内定案） | 底部栏沉浸材质；三种形态（手机/折叠/平板）截图比对 |
| **GL-5 交互动效** | `interactive: true` + `lightEffect` 点光源（触点光感，color 默认白）；按压弹性已有 GlassSurface | 只在**导航类可点组件**上开启光效，避免大面积重绘 | 触摸光效联动；无掉帧（帧率取样） |

**与本次 UI 改造的协同**：§2 的侧栏视图切换器、§3 的 Tab 条 40vp 改造**必须在 GL-2 之前完成**——否则外壳迁移时会把未定稿的侧栏结构一起搬进 `Navigation`，回归范围翻倍。（与 v2 §六第 2 条「外壳先行」的结论一致：**先定结构，再迁外壳**。）

### 4.4 系统组件材质一致性（P2-14，341 条）
API 26 起 `Dialog`/`Toast`/`AlphabetIndexer`/文本选择菜单**默认开启沉浸材质**。需复核：
- 应用自绘玻璃（`GlassSurface`）与系统 Dialog/Toast 并置时的**强度观感一致性** → 用 `MaterialTokens` 对标系统档位，必要时降低自绘档位。
- `Toast` 在本会话高频出现（O4 重建提示等）→ 优先核对。
