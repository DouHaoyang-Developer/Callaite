## 2. 三条路的可行性研究（逐条：机制 + 证据等级 + 结论）

> 证据等级：**Ⓐ = 本窗口设备实测** · **Ⓑ = SDK 原文/源码级** · **Ⓒ = 推断（未实测）**

### 2.1 路径① —— Enter 移到 post-IME：**✗ 不可行（但不同于 W5 的理由）**

**W5 的原结论**：`onKeyEvent`（post-IME）**太晚** —— native 已插换行且必然 `spanIndex error`。
**任务书要求复核**：「post-IME 时**读取**并**修正**，而不是拦不住就放弃」。

#### 本窗口的复核结果（改判理由与 W5 不同 ✗→✓）

**关键实测（Ⓐ）**：把 Enter 从 preIme 移出、改由 **`onKeyEventDispatch`**（post-IME **且** pre-native，
理论上正是「既晚于输入法、又早于 native」的唯一窗口）接 —— **`onKeyEventDispatch` 收不到 Enter 的 Down**：

```
# 同一次会话、同一个编辑器实例（owned=1），逐个键对照：
W9PROBE dispatch code=2013 type=0 owned=1 comp=0     ← ↓ 的 Down 到了
W9PROBE dispatch code=2013 type=1 owned=1 comp=0     ← ↓ 的 Up 也到了
W9PROBE dispatch code=2012 type=0 owned=1 comp=0     ← ↑ 的 Down 到了
W9PROBE dispatch code=2049 type=1 owned=1 comp=0     ← Tab 的 Up 到了（Down 被 preIme 自己消费）
W9PROBE dispatch code=2054 type=1 owned=1 comp=0     ← **Enter 只有 Up，Down 从未到达** ✗
```
- **且与组词无关**：冷启动后**什么都没输入**、直接注入回车，同样只有 `type=1` ✗（Ⓐ）
- **对照组（同一台设备、同一条通道、只换包）**：A 侧 W5 包（Enter 在 preIme）= `W5KEY enter->create-below` ✓、
  磁盘 +3 B ✓ ⇒ **不是「回调没挂上」，也不是「设备坏了」**（Ⓐ ✓ A/B 锁定变量）

> **⇒ 路径① 的真实障碍不是「太晚」，而是「根本收不到」**：本机输入法会把 **Enter 的 Down**
> 在 `onKeyEventDispatch` 之前消费掉（Up 仍放行），而 `onKeyEvent`（更晚）同样拿不到 Down。
> ⇒ 「post-IME 读取并修正」缺少**触发时机**（没有任何 post-IME 回调能可靠报告这次按压）⇒
> **该路在本环境不可行** ✓，不是「没试」。

**顺带更正的 W5 登记（✗→✓，必须留痕）**：W5 记过「挂 `onKeyEventDispatch` 会让**普通字母输入整个失效**」。
W9 用同一设备同一通道复跑：**挂上它、对所有非 Enter 键返回 false** 时 ——
注入 `n` ⇒ `pinyinTextInput text='n'` + `candidateWordText` ×5 ✓；注入 `nihao` ⇒ 合成态与上屏全部正常 ✓；
磁盘字节照常前进 ✓ ⇒ **不成立** ✗。W5 那次更可能是**探针形态**所致（未记录 return 值）。
⚠️ 但**无法复原 W5 当时的写法**，故只记「被复跑推翻」。

## 3. 选定方案与实现

### 3.1 方案一句话

> **Enter 留在 `onKeyPreIme`（保住 W5/W6/W7 的 Enter 语义），但在同一个回调里加一道组词态守卫：
> 「刚见过字母键」⇒ 这次回车**让给输入法**（`return false`）；「没见过字母」⇒ 应用接管。**

### 3.2 实现（`entry/src/main/ets/components/outliner/BlockEditor.ets`）

| 位置 | 内容 |
|---|---|
| `:109-120` | 新增 `private sawLetterKey: boolean = false;` + `static isLetterKeyCode(code)`（`KEYCODE_A..Z = 2017..2042`）|
| `:509-543` | 新增 `private isComposingNow(): boolean` —— `getPreviewText().value.length > 0` 的**兜底**判定（本机恒 false，见 §2.2）|
| `:640-689` | `routeKeyPreIme()`：**字母键 ⇒ 置 `sawLetterKey`**；**Enter ⇒ `sawLetterKey || isComposingNow()` 为真则 `return false`（放行给输入法），否则 `routeKeyEnter(event)`（应用接管）** |
| `:971-977` | `handleBlur()`：复位 `sawLetterKey = false`（**唯一**复位点，理由见 §3.4）|
| `routeKeyEnter()` **函数体一行未改** | 语义逐字保持 W5 形态（行中/Shift ⇒ 块内换行；末尾 ⇒ 建兄弟块）|
| `routeKeyPostIme()` / `build()` **未改** | ↑↓/Backspace 仍在 `onKeyEvent`；`onKeyPreIme`/`onKeyEvent` 的挂载点照旧 |

**净代码增量（去掉注释）**：1 个布尔 + 1 个静态判据函数 + 1 个兜底函数 + 3 处判断（见 `git diff`）。

### 3.3 为什么这样能修好判据④（机制）

```
物理回车 Down
   ↓
onKeyPreIme(Down)  ←── 应用在这里
   ├─ 见过字母键（组词中）⇒ return false（放行）
   │        ↓
   │   input method events ←── 输入法拿到回车 ⇒ 上屏拼音原文、丢弃候选 ✓
   │        （应用侧随后收到 aboutToIMEInput / onIMEInputComplete —— 那是「上屏」不是「抢键」）
   │
   └─ 没见过字母键（非组词）⇒ routeKeyEnter() ⇒ 块内换行 / 建兄弟块 ✓（native 的坏插入被绕开）
```

### 3.4 为什么**不在「输入法提交」时复位** `sawLetterKey`（这是设计要点，不是遗漏）

本机**组词提交恰好发生在回车那一刻**（实测时序：`preIme(2054)` → **紧接着**
`aboutToIMEInput val=n` / `onIMEInputComplete`）。若把复位挂在「提交」上（例如 `onDidChange`），
就会得到「**复位之后紧跟着回车**」的序列；而 §2.1 已证明「放行之后输入法会把回车吃掉」
⇒ 那个回车会**凭空消失** ✗ —— 恰好又制造出「回车没反应」的 bug。
⇒ 复位点**只有焦点离开本块**（`handleBlur`），与实测装置一一对应。

### 3.5 为什么不破坏 W5/W6/W7 的 Enter 语义

| 已验收能力 | 为什么不受影响 | 本次实测（Ⓐ）|
|---|---|---|
| **末尾回车建兄弟块** | 该路径要求 `sawLetterKey=false`；验收装置本来就是「点击块正文 → 注入回车」（没有字母到达应用） | `W5KEY enter->create-below … ok=1`；**3399→3402 B（+3）** ✓ |
| **块内换行（行中 / Shift）** | 同上（进入 `routeKeyEnter` 后逻辑一字未改）| `W5KEY enter->newline caret=8 len=8 n=1`（Shift+Enter）✓ |
| **Tab / Shift+Tab** | 走的是 `routeKeyPreIme` 里 **Tab 分支**，本次只在其**前面**插入字母/Enter 判断，Tab 分支本体未改 | `W5KEY preIme tab shift=0 n=2` / `shift=1 n=3` ✓ |
| **跨块 ↑↓** | 仍在 `routeKeyPostIme`（本次完全未改）| `up->prev block=8922…` / `down->next block=e0fa…` ✓ |
| **Backspace 空块** | 同上（未改）| 磁盘 **3403→3402 B（−1 … 实测块被删）** ✓ |
| **W6 回车焦点闭环** | 未触碰 `setFocusedBlock` 的下一帧排程与 `BlockAnchorService.revealBlockDeferred` | 建块后新块照常成为焦点块 ✓ |
| **W7 四项按键 + W8 按键契约** | Tab/Shift+Tab/↑/↓/Esc 的落点与判据全部未改 | 见上 ✓ |

### 8.2 保守项（**有意为之**，代价已写清）

**「块内打过字之后的那一次回车」在本机会让给输入法一次**（不建块、不换行）。
- **实测依据**：本机输入法在**非组词**态也会吃掉被放行的回车（§2.1 的 L1/L3/L4 三次注入，
  磁盘与 DOM 逐字节不变）⇒ 这不是本方案造成的，而是「放行 = 交给输入法」的必然结果。
- **为什么仍要这样取舍**：若把守卫收紧到「只有确实在组词时才放行」，就必须**读到合成态** ——
  而 §2.2 已实测**读不到** ⇒ 只能二选一：**修好判据④**（本窗口的目标，S3 出口条件）
  或**保住「打字后回车」**。选前者，并把它登记为已知代价 ✓。
- **影响面**：只在「同一块内打过字」之后的那一次回车；用户再按一次（或先点别处再点回）即恢复正常 ✓
  （`handleBlur` 复位）。**W5/W6/W7 的验收装置全部是「点块 → 注入回车」⇒ 不受影响** ✓（§6 R1–R7 实测）。
