## 2. 那「12 个块」到底去哪了？—— 我复现出的真实丢失路径 (a)

虽然 W1b 的具体 32→20 现场不可回溯，但**同一页面上存在一条确定的数据丢失路径**，
且它与 W13-3 登记时留下的那条线索**精确吻合**：

> `S3-W13-FindInPage跳块.md:283`：「疑与**连续空 `- ` 行**（本夹具全部由 `Enter` 注入、**几乎全空**）的装载/索引有关」

### 2.1 根因（文件:行号）

`entry/src/main/ets/core/parser/MarkdownParser.ets:55-65`（**修复前**）

```ts
} else {
  // 无 frontmatter：行首第一个 -  之前的内容都是页面元数据
  for (let i = 0; i < lines.length; i++) {
    const trimmed = lines[i].trim();
    if (trimmed.startsWith(BLOCK_PREFIX)) {   // BLOCK_PREFIX === '- '
      metadataEndIndex = i;
      break;
    }
    metadataEndIndex = i + 1;                 // ← 每一行都推进
  }
}
```

**两个缺陷叠加**：

1. **`'- '.trim()` === `'-'`**（尾部空格被 `trim()` 吃掉）⇒ **空块行不满足 `startsWith('- ')`**
   ⇒ 空块行被当成「页面元数据」✗。
   而「是否 Block」的判据是 `countIndent().isBlock`（`MarkdownParser.ets:295-321`），
   它对空块行的答案是 **true** ✓ ⇒ **两套判据对空块行不一致** ✗。
2. `metadataEndIndex = i + 1` 写在**每一行**上（不在 `else` 的 continue 语义里）⇒
   只要文件里**一个「非空 `- ` 行」都没有**，边界就被推到 `lines.length`
   ⇒ 元数据区**吞掉整个文件** ⇒ `blocks.length === 0`。

**后果链**（与 W1b 观察到的现象同形）：

```
文件：开头 N 个空块（`- `），内容行在很后面（或完全没有）
  ↓ parse
块数骤减：只剩「第一条非空块行及其之后」的块  ⇒ 状态栏计数 < 磁盘块行数   ← 这就是 W13-3 的「20 vs 32」
  ↓ 任何一次编辑触发 flush → savePage → MarkdownExporter.export(内存里的少数块)
磁盘被改写成内存模型：**前面那一整段空块永久消失**  ← 这就是 W1b 的「32 行 → 20 行」
```

### 2.2 离线复刻实测（修复前 vs 修复后）

复刻器逐行照搬 `MarkdownParser.ets` / `MarkdownExporter.ets` 的逻辑：

| 输入（磁盘原文） | 修复前导出 | 修复后导出 |
|---|---|---|
| 32 行全为 `- `（95 B） | **0 B** ✗ 全丢 | **95 B** ✓ 逐字节相同 |
| 20 行全为 `- `（59 B） | **0 B** ✗ 全丢 | **59 B** ✓ 逐字节相同 |
| 19 个空块 + 尾块 `- X`（20 行 / 60 B） | **3 B** ✗ 丢 19 块 | **60 B** ✓ 逐字节相同 |
| **31 个空块 + 尾块 `- a`（32 行 / 96 B）** ← **W1b 的行数形态** | **3 B** ✗ 丢 31 块 | **96 B** ✓ 逐字节相同 |

⇒ **「32 行 → 1 块」在修复前是确定可复现的** ✓ —— 与 W1b 的「32 行 → 20 行」**同族**
（差别只在于内容行出现在第几行：内容行越靠后，丢得越多）。

> ⚠️ **必须说清的边界**：我**不能**断言 W1b 那一次的 32 行文件**就是**这个形状 ✗
> （原文已被覆盖，无法回溯 ⇒ 纪律 9：高危断言必须独立复现，我只能复现**机制**，不能复现**那一次**）。

### 2.3 与 W1b 记录的数字是否自洽？

## 3. 修复（最小改动）

**只改一处**：`entry/src/main/ets/core/parser/MarkdownParser.ets:55-77`
（无 frontmatter 分支的元数据边界判定）。

```ts
} else {
  // 新判据：元数据 = 文件开头**连续**的 `key:: value` 行
  for (let i = 0; i < lines.length; i++) {
    const trimmed = lines[i].trim();
    if (trimmed === '') {
      continue;                                  // 空行中性：不推进、不终止
    }
    if (PROPERTY_REGEX.exec(trimmed)) {
      metadataEndIndex = i + 1;                  // 只推进到真正像元数据的行
    } else {
      break;                                     // 第一条非属性行 = 内容起点
    }
  }
}
```

**为什么是这个改法**：

- **判据换对了**：不再用「像不像块」，改用「像不像元数据」（`PROPERTY_REGEX`）。
  空块行既不匹配 `PROPERTY_REGEX`、`trim()` 后也不是空串 ⇒ 立刻 `break` ⇒ 边界落在**内容起点** ✓
- **不动 frontmatter 分支**（`lines[0].trim() === '---'`）⇒ 有 frontmatter 的文件行为**逐字节不变** ✓
- **保持不变式**：文件开头没有任何属性行 ⇒ `metadataEndIndex === 0`
  ⇒ 内容**全部**交给块循环，**不静默吞行** ✓
- **不放宽既有契约**：纯文本行仍然解析出 0 块
  （`MarkdownRoundTrip.test.ets:175-184` 的「无前缀 → 0 块」契约**未变** ✓）
