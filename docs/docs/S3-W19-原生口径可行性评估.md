## 2. ② 编辑器：ArkUI 原生能否达到 Obsidian 级体验

### 2.1 先纠正前提：**Obsidian 本身就是 Electron**

Obsidian 的编辑器是 **CodeMirror 6（web 技术栈）**，整个应用跑在 Electron 里 ✓。
⇒ **「web 技术 ⇒ 体验差」不成立** ✗ —— 用户实际感知的「原生体验」应拆成**交互质量维度**：
输入延迟 · IME 正确性 · 光标与选区精度 · 滚动跟手 · 无卡顿 · 手势与快捷键 ✓
**⇒ 判据应是「这些维度做不做得到」，不是「用的什么栈」** ✓

### 2.4 短板 2（**当前是缺陷，不是能力边界**）：组词中回车被 `onKeyPreIme` 截胡

**机制** ✓（`AGENTS-归档.md:175-177`，W8 在 **2in1** 上 A/B 判负）：
`BlockEditor` 的 `onKeyPreIme` **返回 `true`** ⇒ SDK 顺序 `preIme → keyboardShortcut → **input method events** → onKeyEventDispatch → onKeyEvent`
⇒ **应用抢在输入法之前消费回车** ✗ ⇒ 组词回车上屏被破坏。
矩阵 **E15 判据④「组词中硬件回车」= ⚠️ 部分**（**这本是 S3 的出口条件**）⇒ 归置 **R0-3**。

**⚖️ 关键判断**：这是**可修的实现选择**，**不是「原生做不到」** ✓ ——
`BlockEditor.ets:817-830` 已记 W9 的落点结论（Enter 必须由应用侧在 pre-IME 接管，因为 native 自插换行会报 `spanIndex error`），
缺的是**一道可靠的「正在合成」守卫** —— 而 **`sawLetterKey` 守卫已在**（`:114-116`、`:686`）✓。
⇒ **归属 = 缺陷修复，不是路线否决** ✓

**❌ 短板 3（两边都缺）：IME 合成态「没有应用侧信号」**

`BlockEditor.ets:511-519` 对 `RichEditor` 的**全部 IME 通道逐条核查**后的结论（原文）：

| 通道 | 时机 | 组词期间实测 |
|---|---|---|
| `getPreviewText()`（`:2307`） | 任意时刻可读 | 控制器可用，**但组词态 `value` 恒为空（len=0）** ⇒ 拿不到合成文本 |
| `aboutToIMEInput`（`:2807`） | IME **提交**之前 | **0 次**；只在上屏那一次触发 |
| `onIMEInputComplete` / `onDidIMEInput`（`:2831/:2853`） | 提交**完成**之后 | 属「已上屏」信号，无法用于「上屏前」判断 |
| `@ohos.inputMethod` 公开面 | — | `getInputMethodState()` 只回 `EnabledState`；`on('setPreviewText')` 是**输入法应用**侧，普通应用报 **`12800004 - not an input method application`** |

**SDK 侧独立佐证** ✓：`KeyEvent` **无任何合成态字段**（`common.d.ts:11038-11182`，逐字段核对）；
`enablePreviewText` 默认 **true**（`rich_editor.d.ts:3024-3025`）—— 开了也拿不到（见上）✓

**⇒ 而 web 侧本来有更可靠的东西** ✗✓：
web 标准有 **`compositionstart` / `compositionend` / `compositionupdate` / `KeyboardEvent.isComposing`**（Chromium/ArkWeb 成熟）✓
**但本仓 `WebEditor` 没有用它** ✗ —— 全仓 `compositionstart|compositionend|isComposing|compositionupdate` **0 命中** ✓；
它的页内层用 **`document.execCommand`**（**已废弃 API**）做 bold/undo/redo/formatBlock（`WebEditor.ets:256-274`）✗

> ⚠️ **这条对结论的影响是双向的，必须如实说** ✓：
> **「WebView 承载编辑器」在 IME 合成态这一项上，理论上可以比原生 `RichEditor` 更强**（web 有标准合成事件，原生没有等价信号）；
> 本仓的 `WebEditor` 之所以更差，是**它的实现陈旧**，**不是 WebView 的固有限制** ✗✓。

### 2.6 ② 的结论（**逐条**）

1. **「ArkUI 原生编辑器能否达到 Obsidian 级体验」= 能** ✓ —— 依据：SDK 面（光标/选区/span/装饰线/真底色/缩进/自定义菜单）**已足够覆盖 Obsidian 的编辑器交互面**，
   且本仓**已用这套 API 跑通 E1–E20 的 20 条验收**（含逐键落盘、Tab 缩进、撤销重做逐字节回原值、跨块 ↑↓、块内换行）✓
2. **哪些维度不能 / 未证明** ✗：
   - **大文档性能（红线①②③ + fps）= 未证明**（E17/E18/E19/E20 全部归置 R0）⇒ **「流畅度达标」这句话现在还不能说** ✓
   - **IME 组词回车 = 当前不达标**（E15 ⚠️、2in1 A/B 判负）—— 但**可修** ✓
   - **IME 合成态可观测性 = 原生无信号**（结构性）—— 需靠「post-IME 让位 + 字母键守卫」这类**间接**手段规避 ✓（W11 已给出可行机制）
3. **「WebView 承载编辑器」的代价 = W-1（光标不上报）为主**，其余为工程量；
   而 **IME 一项 web 标准反而更强**（§2.4）⇒ **不能笼统说「WebView 编辑器体验差」** ✓
4. **⚠️ 全部结论的证据边界**：本仓的一切编辑器实测都在 **`MatePad Pro 13` 模拟器** + **注入键**上取得，
   而陷阱 21 钉定**平板注入键不过 IME** ✗ ⇒ **IME 相关结论在真机上可能不同** ✓
   **真机 + 真实物理键盘 + 真实中文输入法的终验（S4-A / 判据④）尚未做** ✗✓ ⇒ **不得写成「已达 Obsidian 级」** ✓
