## 1. 挂点分析（**先读 W2 实现，不猜**）

### 1.1 三层落盘链路的实际结构（源码核对）

任务书写「在 W2 做的 `flushSave` 800ms 防抖之后挂防抖重建」；实际读码后必须**更正挂载层**，
否则会把对账挂在一条**B 形态根本不走**的路径上。

| 层 | 文件:行号 | 事实 |
|---|---|---|
| **W2 的 `flushSave`** | `components/outliner/IntegralEditor.ets:126` | **整页编辑器（`IntegralEditor` / live 模式）自己的 800ms 防抖**。它做的是「编辑器文本 → `toMarkdown()` → `replacePageBlocks()`」，即**整页重建块**，属结构性写 |
| **B 形态的落盘链** | `services/DirtyPageTracker.ets:61/95/131` | `EditorService.updateBlockContent`（`:206`）→ `OutlinerEngine.execute`（`:57`）→ `persistForOp`（`:511`）**文本类只 `markDirty`**（`:515`）→ 由 flush 时机（失焦/切页/进后台/销毁前/**5s 硬截止**）→ `DirtyPageTracker.flushPages`（`:131`）→ 注入回调 `OutlinerEngine.persistNow`（`:567`）→ `DataStore.savePage` |
| **即时链（结构性）** | `OutlinerEngine.ets:525/529/551` | `persistForOp` 结构性分支：先 `flushNow()`，再 `persistNow(pageId)` → `DataStore.savePage` |
| **唯一的写盘出口** | `core/db/DataStore.ets:339` `savePage`，`:347` `fileRepo.writeTextSync` | `writeTextSync` 全仓**只此一处调用**（`FileRepository.ets:129` 是定义）⇒ **`savePage` 是「正文已落盘」的唯一收敛点** |

**⇒ 结论**：`IntegralEditor.flushSave` 是**整页编辑器**的防抖，不是 B 形态的落盘链路。
把对账挂在那里，B 形态（`EDITOR_IMPL = 'native'`，当前主径）**一次都不会触发**。
故选 `DataStore.savePage` —— 它同时是两条链的下游，且是唯一写盘点。

### 1.2 挂点位置（文件:行号）

```
core/db/DataStore.ets:339  savePage(pageUuid)
  :341-346   取 page / blocks / export markdown / joinPath
  :347       fileRepo.writeTextSync(fullPath, markdown)     ← 写盘（既有）
  :348       page.updatedAt = Date.now()                     ← 既有
  :349-377   ── S3-W1 挂点说明注释 ──
  :378-383   try { indexStore.reindexPageReferences(pageUuid, blocks) } catch { 记错误 }
```

**为什么必须在 `writeTextSync` 之后**（而不是之前）：写在之前的话，一旦写盘抛异常，
内存索引已经被改成「磁盘上并不存在的内容」——**索引会先于磁盘说谎**。
现在的次序下：写失败 ⇒ 抛异常 ⇒ 对账不执行 ⇒ 索引保持上一次的真实值 ✓。

**为什么用 `try/catch` 包住**：索引是**派生数据**。写盘成功即算成功；
对账失败只记日志，不连累落盘（下一次落盘会重新对账，因为内容快照不匹配 ⇒ 自动重算）。

### 1.3 为什么不是「再调一次 `rebuildReferences`」

这是与任务书字面表述的**第二处偏离**，理由必须写清：

`IndexStore.rebuildReferences`（改前 `:213`）的实现是

```ts
for 每个 block: for 每个 block.refs: this.addReference(block.uuid, ref, false)
```

而 `addReference`（`:180`）**只做去重追加，没有任何删除语义** ⇒ 该函数是「**只加不减**」的。
它的成立前提是「索引为空」或「这批块此前从未登记过」——即**页面初次载入的播种**。
把它挂到落盘链路上会得到一个**看起来对、实际只修一半**的结果：

- 新增 `[[x]]` ⇒ 反链出现 ✓（这一步能做对）
- **删除 `[[x]]` ⇒ 反链永远不消失** ✗（旧条目留在 `backlinkIndex` 里）

⇒ 这正是计划明文要求防的「**只修一半**」。故本窗口在索引层新增两个方法（§2），
把「重建」改成「**对账**」（可增可减）。

### 1.4 附带发现：读取时机也会造成**假阴性**（顺手加固）

即便索引已经正确，面板仍可能显示成 W12-3 的样子 —— 因为**读得太早**：
`RightSidebar` 的 `@Watch('callaite_focusedBlock')`（`:68/83`）注释写着「挂它只为驱动反链刷新」，
而文本输入是惰性落盘 ⇒ 这个回调可能在「5s 兜底未到、也没失焦」时读到**还没对账**的索引。
现象与 W12-3 **逐字相同**，但根因完全不同（一个是索引从不更新，一个是读得太早）。

⇒ 新增 `WorkspaceService.getBacklinksFresh()`（`:203`）= **先 `flushDirtyPages()` 再读**，
并把三处反链读取点改用它（`RightSidebar.ets:89/449/665`、`BacklinkFilters.ets:137`）。
`flushNow()` 在无脏页时 O(1) 直接返回（`DirtyPageTracker.ets:95-100`）⇒ 绝大多数调用零开销。
**索引口径一个字没改**，只改了读取时机。

## 3. 复杂度分析与防抖间隔（计划要求：先测成本再定间隔）

### 3.1 逐层拆解（Ⓑ）

记：`B` = 本页块数，`R` = 本页引用总数，`T` = 某个目标名下的条目数，`E` = **全库**反链条目总数。

| 步骤 | 实现 | 复杂度 |
|---|---|---|
| 圈定本页相关块 | 遍历 `blocks` + 遍历 `blockPageIndex` | `O(B + 全库块数)` |
| 清场（摘悬空/失效条目） | 遍历 `backlinkIndex` × 每个目标名的条目数组 | **`O(E)`** |
| 作废被摘块的快照 | 遍历 `blocks` + Set 查询 | `O(B)` |
| 逐块刷新 | `reindexBlockReferences`，内容没变即短路 | `O(改动块数 × (|content| + 新引用数 × T))` |

**关键否证**：任务书点名要防的是「`Θ(块数 × 引用数)` 或更差」。逐项检查：

- **没有 `O(B²)`、没有 `O(B × R)`**。清场那一遍是 `O(E)`，与**库规模**成正比、与页面大小无关；
  它**不是**二次项，因为每个条目只被访问一次。
- 唯一可能出现的二次形式在 `addReference` 的 `findIndex`（`:186`）：同目标下有 `T` 条时，
  每加一条要扫 `T` ⇒ 若 N 个块引用**同一个**目标则退化成 `Σᵢ i = O(N²)`。
  但这项**不是本窗口引入的**：改前的 `rebuildReferences` 里一模一样。
  实测该病态输入（2000 块 / 1000 条同目标引用）整页成本 **3.42 ms（旧）vs 3.09 ms（新）** Ⓒ
  ⇒ **同一条成本，本窗口没有把它变大**。
- 本窗口真正的增量点是：**正则扫描次数从「每块每次落盘」降到「本次真正改动的块数」**。

### 3.2 实测数据（Ⓒ 受控离线探针，**非设备数据** ✗）

探针 `w1_cost_probe3.js`：`IndexStore.reindexPageReferences` 的**逐行移植**，1000 块页。
> ⚠️ **量法陷阱（第一版量错了，记录以免重犯）**：第一版对被测函数「预热两次再计时」——
> 而该函数**第一次调用就会把状态改掉**（把块标记成已索引）⇒ 计时的第三次命中短路、恒返回 0 次扫描，
> 量到的是**空跑成本**而不是对账成本 ✗。**带状态的被测对象不能预热后复用**；
> 本版改为每个用例新建实例、只测一次。

### 3.3 防抖间隔的选择与理由（**写明是估算，真机需实测** ✗）

**结论：不新增计时器，沿用既有的 `DirtyPageTracker.BACKSTOP_MS = 5000 ms`**（`DirtyPageTracker.ets:36`）。

理由三条：

1. **它已经是一个防抖器**，而且比 800ms 更保守 —— `armTimer()`（`:115-123`）只在「当前没有排程」时
   武装一次，**刻意不顺延**（注释明写「定时器是**截止期限**而非静默窗口」）。
   ⇒ 连续打字期间最多每 5s 落盘一次，对账跟着落盘走，**天然被防到同一节奏**。
2. **在它内部再套一层 `setTimeout` 收益为负**：那只会把索引的陈旧窗口从「写盘时刻」
   推迟到「写盘后 N ms」，同时新增一个必须与脏页集合 / 组件生命周期对齐的状态
   （脏页被 `flushPages` 清空、页面可能被删除、tab 可能被关）—— 这是纯新增风险。
3. **实测成本支持这个间隔**：稳态每轮落盘 0.06–0.19 ms，最坏一档 1.85 ms。
   把间隔压到 800ms 甚至 200ms 也「跑得动」，但那等于让索引比磁盘更勤 —— 与「对账挂在落盘之后」
   的语义自相矛盾；索引的职责是**不落后于磁盘**，不是领先于它。

> **⚠️ 必须写明的边界**：以上间隔是**代码级估算 + 宿主 Node 量测**的结论 ✗。
> 真机（尤其低端机 / 1018 块压测页 / 引用密集页）必须按 §6 的判据复测后**再定稿间隔**；
> 若真机实测最坏一档 >50 ms 或出现单次 >150 ms 停顿，则应改为**分片重建**
> （把逐块刷新按帧切片），而不是调大间隔 —— 调间隔只降低频率，不降低单次上界 ✗。

### 3.4 正面回答：**会不会把 A-2 消掉的无界停顿搬到索引层？**

**不会** ✓。三条独立理由，缺一不可：

1. **实现是增量的（结构性理由）**：正则扫描次数 = 「本次真正改动过的块数」。
   实测「无改动再次落盘 = 扫 **0** 块」、「改 1 块 = 扫 **1** 块」。
   A-2 的病态输入（`!`×8000 / `!`×20000 单块）在新实现下**扫描次数恒为 1**，
   成本是**单块** content 长度的一次正则 —— 与全文规模无关 ✓。
2. **没有随规模放大的项（复杂度理由）**：见 §3.1，清场那遍是 `O(E)` 线性；
   唯一可能的二次项（`addReference` 的 `findIndex`）**新旧实现同款**，实测 3.42 → 3.09 ms 未放大。
3. **最坏一档有量化上界（实测理由）**：1000 块页**首次**对账 1.85 ms = A-2 上界的 **0.32%**，
   且「首次」每个页面生命周期只发生一次（页面载入后第一次落盘）✓。

> **⚠️ 一条未闭合的边界** ✗：`reindexPageReferences` 的清场那遍是 `O(E)`，**E 是全库条目数**。
> 若将来出现「全库十万级引用 + 每次落盘」的形态，这一遍会成为新的固定成本。
> 本次未构造该规模夹具、也未实测 ⇒ **登记为待验收**（§6 的 V4）。

`blockTree.getPageBlocks(pageUuid)`（`DataStore.ets:344`），**不是缓存**，
所以它看到的是 `doUpdateBlock` 刚写进去的**新 content** ✓。

### 4.2 路径②：**删除** `[[x]]` ⇒ 反链消失

前半段与 ① **逐行相同**（同一条 `update-block` → 标脏 → flush → `savePage` 链），
分歧只在索引层：

```
  → DataStore.ets:379   reindexPageReferences
  → IndexStore.ets:237  reindexBlockReferences(该块)
  → IndexStore.ets:238  快照不等（content 变了）⇒ 不短路
  → IndexStore.ets:242  removeBlockReferences(block.uuid)   ← ★ 先摘旧条目
  → IndexStore.ets:243  extractPageRefs(新 content) ⇒ []    （引用已被删掉）
  → 不 addReference 任何东西
  ⇒ backlinkIndex['x'] 里该块条目被摘除；若该目标名下再无条目，
     整个 key 也在 removeBlockReferences 的重建里被丢掉（:406-412）
  ⇒ getBacklinks('x') 返回 [] ⇒ 反链消失 ✓
```

**这一条正是「只加不减」做不到的那一半** ✗ —— 也说明为什么必须新增
`removeBlockReferences` 调用而不是复用 `rebuildReferences`（§1.3）。

### 4.3 离线探针：30/30 通过（Ⓒ）

探针 `w1_backlink_probe.js`：把 `reindexBlockReferences` / `reindexPageReferences` /
`removeBlockReferences` **逐行移植**为 Node 脚本（数据来源换成普通对象），断言 30 条。

### 4.4 探针抓出的两处真问题（**已在本窗口修掉**）

**问题 ①：摘除条目与「已索引」快照不自洽 ⇒ 第二次落盘反链归零** ✗

第一版 `reindexPageReferences` 的清场**无条件摘掉本页全部条目**，然后靠
`reindexBlockReferences` 逐块重建；而后者被 `contentIndexed === content` **短路**。
⇒ 条目被摘了、重建被跳过 ⇒ **索引静默清空**。
探针实测现场：1000 块页第 501 块写着 `[[x]]`，第一次落盘后 1 条，**第二次落盘后 0 条** ✗。

**修法**：立下不变量 —— **任何摘除条目的地方，都必须同时把该块的快照打回空串**。
并进一步把清场改成**只摘失效条目**（悬空 / 本页已删或被换代的块），**活块的条目保留**
⇒ 既守住不变量，又让「内容没变的块零动作」真正成立（这才是增量）。

**问题 ②：删除块未作废快照 ⇒ 删除→撤销后反链永久消失** ✗

被删块进 `recycleBin` 时**内容一个字没改** ⇒ 快照仍等于 content。
撤销（`BlockTree.restoreFromRecycleBin`，只搬 blockMap/childrenMap）把块原样放回后，
下次对账认为「这个块早已索引过」而**跳过重建** ⇒ 反链永久丢失。
这正是 AGENTS **陷阱 16** 的同族：「**撤销能落盘 ≠ 撤销恢复对了**」。

**修法**：`OutlinerEngine.invalidateDeletedRefs`（`:228`）在 `doDeleteBlock`/`doDeleteBlocks`
里把被删块的 `contentIndexed` 打回 `''`（与 `restoreBlockIndex` 补索引那一步配套）。
