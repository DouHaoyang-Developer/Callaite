## 3. 任务 ②：**修法选择**（`onNewWant` vs 改 `launchType`）

### 3.1 两条路都是「真路」，不是「一条对一条错」 ✗✓

| 路线 | 机制 | 与现象的关系 |
|---|---|---|
| **A. 补 `onNewWant`** ✓（**本窗口选它**）| 保持 `singleton`，**接住**系统已经调进来的 `Want` ✓ | 系统已经调了 `onNewWant`（§2.3 Ⓐ ✓）⇒ **补上就是补上缺失的入口** ✓ |
| **B. 改 `launchType: multiton`** | 每次拉起**新建一个 Ability 实例** ⇒ 每次都走 `onCreate` ✓ | **同样能修好** ✓ —— 但**改的是「实例策略」而不是「入口」** ✗ |

⚠️ **必须说清**：B **不是错的**，它**也能让第二次分享落盘** ✓ —— 所以**不能**把 B 说成「不可行」✗。下面只讲**为什么 A 更好** ✓。

### 3.2 选 A 的理由（逐条，按权重）

1. **A 是这套生命周期的「约定入口」，且设备证据表明系统本来就在用它** ✓✓（§2.3：`[JUA2177] JsUIAbility call js, name: onNewWant` ✓）
   ⇒ `singleton` 的契约就是「**首次 `onCreate`、此后 `onNewWant`**」；补 `onNewWant` = **忠实实现约定** ✓。
   B 则是**改约定去绕过一个没实现的回调** ✗。
2. **B 有可观测的副作用：窗口/任务增生** ✗ —— **实测**：一次 `aa start`（`-uiLayout`/`mission` 均可见）即**新建一个窗口**；
   开工时 `aa dump -l` 就有 **#108 + #109 两个 Mission** ✓（§1）。`multiton` 下**每次分享都会再多一个** ⇒
   用户分享 10 次得到 10 个 Callaite 窗口 ✗ —— 这是**新增缺陷**，不是修复 ✓。
3. **A 的改动面最小、且不碰配置** ✓：只改 **1 个 `.ets`**；B 要改 `module.json5`（且 `launchType` 属**包结构**，
   与 `main_pages.json` 无关 ✓ —— 任务里那句「除非 `launchType` 真的配在那里」的担心**可以排除** ✓）。
4. **A 天然复用 `setCurrentPage` + `bumpBlocksVersion` 的既有语义** ✓ —— 同一实例同一窗口，不会重复 `loadContent`；
   B 每次分享都跑一次完整的 `onCreate` + `onWindowStageCreate` + `loadContent`（含 `FileService.initGraph()` 全量重载 ✗）。

### 3.3 公共路径抽取（**避免两份逻辑分叉** ✓✓）

**改前**（只有一条路）：`onCreate` 里做 3 件事（`setContext` · `initGraph` · `extract`+暂存），`onWindowStageCreate` 回调里处理。

**改后**（两条路共用）：
```
onCreate(want)        ──┐
                        ├─→ acceptShareText(want, source)  → pendingSharedText += text
onNewWant(want)       ──┘        （唯一的「读 want」实现 ✓，onCreate/onNewWant 都不各写一份 ✓）
                                        │
                    stageReady ? ───────┴───────────────
                       │ true                          │ false
             processPendingShare()            （暂存；等 loadContent 回调里
              ← isUrl ? handleSharedUrl       onWindowStageCreate 的
                       : handleSharedText      processPendingShare() 统一处理）
```
**净改动**：`+67 / −1`（那 1 行删除是 `onCreate` 里被抽走的那句 `this.pendingSharedText = this.extractSharedText(want);` ✓）。

⚠️ **一个差点踩进去的坑（本窗口自查拦下）** ✗✓：第一版把 `FileService.setContext()` + `FileService.initGraph()`
**一起**放进了公共路径 —— 于是**每次 `onNewWant` 都会调一次 `initGraph()`** ✗。
但 `FileService.initGraph()` → `WorkspaceService.loadGraph()` → `DataStore.loadGraph()` 会
**`indexStore.clear()` 后全量重读整个 vault**（`DataStore.ets:50-63` ✓）⇒ **每次分享重载整个 Graph** ✗。
⇒ 已改回：**文件服务初始化留在 `onCreate`（冷启动）**，公共路径**只做「读 want + 追加」** ✓。

### 3.4 「连点两次分享」的语义判据（**本窗口拍板** ✗✓）

**结论：不做内容去重；每一次分享都落一个块** ✓✓。

**判据链** ✓：
1. **缺陷的名字不是缺陷的本质** ✗：登记名是 `W11-A`「去重」，但**真正的缺陷是「第二次静默丢弃」** ✓
   —— 「同一内容该不该去重」是一个**产品语义问题**；「第二次内容消失」是一个**数据丢失问题** ✗✓。修的是后者 ✓。
2. **用户的动作 vs 应用的猜测** ✗✓：**「用户点了两次分享」是用户的动作** ✓；
   **「这两次应该只留一份」是应用的猜测** ✗。**静默丢弃 = 应用替用户做了决定** ✓ ——
   与本会话一贯的口径「**数据丢失 > 一切**」直接冲突 ✓（同 W2 的静默丢块、W7 的 OOM 崩溃 ✓）。
3. **仓内一致性** ✓：`insert-block`（手动建块）、导入、插件 `insertTodayBlock` **都不按内容去重** ✓
   ⇒ 分享路径单独去重会造成「同一份内容，从不同入口进来行为不同」✗。
   （反例参照：插件那条**按天幂等守卫**是**有意**的、且是**页面级**的、有明确产品理由 ✓ —— 分享没有对应的理由 ✗。）
4. **可撤销性** ✓：多一个块**用户能自己删掉**（代价小 ✓）；而**没有的块，用户无从恢复** ✗✓。
5. **若将来真要「去重」** ✓：它应当是一个**用户可见**的能力（例：toast 明说「重复内容，已跳过」）
   并可被用户覆盖 ✓ —— 而**不是在这里静默比对字符串** ✗。

**实证**（§5.3 D4/E4）：**同一内容连发两次 ⇒ 磁盘再多一个块、UI 再多一行** ✓✓（不是 +0 ✓）。
