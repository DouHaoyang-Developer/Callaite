## 1. 任务①：先核实（**动结构前必须做**）

### 1.1 W6 排除的三条候选修法 —— 各自的坑，以及本窗口如何绕开

| # | W6 的候选 | W6 的判决 | **坑的精确形态** | **本窗口如何绕开** ✓ |
|---|---|---|---|---|
| ① | **把外层 `Scroll > Column > ForEach(days)` 换成 `List > LazyForEach(days)`** | ✗ 不足以修复 | 外层只有 **7 个 item**，而「`2026-09-30` 那一天」本身就是**一个 1037 行高的 item** ⇒ `List` 仍把它**整体构建** ⇒ 节点数几乎不降 ✗✓ | **不改外层容器的类型，改 item 的粒度**：把「天 × 块行」**拍平成一个序列**，一个 item = **一个块行**（另有 header / tasks / empty 三种小 item）⇒ 1037 块那一天的 1037 行变成 **1037 个独立 item** ⇒ 逐个虚拟化 ✓ |
| ② | **给每节一个有界高度的内层 `List`** | ✗ 引入双层滚动 | `Scroll` 套 `List` = **双层滚动**，本仓在 **S1-B 明确消除过**（`ContentArea`/`PageView` 的 diff 里写着）；且「每节固定高度」与「空日期只有一行」的语义冲突 ✗ | **本页只剩一个滚动容器**：`JournalFeed` 自己就是那个 `List`，节内**不再有任何滚动容器**；`BlockList` 在本页已完全不参与渲染 ✓（S1-B 的「不引入双层滚动」约定被完整保留 ✓） |
| ③ | **只渲染有内容的日期** | ✗ 实测无收益 | 5 个空日期节各只值 1 个 `EmptyState`（约 10 节点）⇒ 不解决问题，反而改变行为 ✗ | **空日期节照旧整节渲染**（`FeedRowKind.EMPTY` 一个 item）⇒ **行为不变** ✓；收益全部来自虚拟化 ✓ |

> **结论**：**唯一同时满足「虚拟化生效 / 不引双层滚动 / 不改变空日期行为」的形态，就是把 item 粒度拍到「块行」这一级** ✓✓
> 这正是 W6 在 `W6-F2` 里写的「用一个 `List` + `LazyForEach` 承载『日期标题 + 块行』（需新增一个扁平化数据源）」✓

### 1.2 「拍平」的代价 —— 逐条核实

| 问题 | 处理 | 依据 |
|---|---|---|
| **节的标题怎么表达** | 成为序列里的 **`FeedRowKind.HEADER`** item。字号/字重/颜色/padding/opacity **逐字段沿用**旧 `ForEach` 内那份（含 `index === 0 ? 20 : 32` 的 padding 与 `1 : 0.85` 的 opacity）✓ | Ⓑ 逐字段对照 |
| **空态怎么表达** | **`FeedRowKind.EMPTY`** item ⇒ 渲染旧 `BlockList.EmptyState()` 的同一观感（`Circle` + `t('placeholder_block')`），`onClick` 走**同一个**懒创建逻辑（`createPage` → `executeOp(insert-block)`），只是把它从 `BlockList` 搬到 `JournalFeed`（旧的内嵌分支已删）✓ | Ⓑ |
| **今天的任务面板怎么办** | **`FeedRowKind.TASKS`** item（仅 `index === 0` 插入一个）—— 位置与旧代码 `if (index === 0) { TaskDashboard() }` **同址** ✓ | Ⓑ |
| **`TaskDashboard` 当 item 会不会拉伸** | 不会：它根节点是 `Column().width('100%').padding(10)`，**内容定高**；无任务时是 `Column().width(0).height(0)`（实测在 dump 里是一个**零高 `ListItem`**：`[1195,658][1974,658]`）✓ | Ⓐ |
| **滚动位置语义 / 跨节滚动** | 唯一滚动容器是这一个 `List` ⇒ 跨节滚动是**同一个列表的连续滚动**（不再有「外层 Scroll 滚动 + 各节 Column 撑高」的分层）；`onReachEnd`（触底追加 7 天）由该 `List` 承担 ✓ | Ⓑ |
| **`LazyForEach` 的 key** | `kind + '|' + day + '|' + uuid` ⇒ 四种 item 各自唯一；块行 uuid 全局唯一（与整页模式同一 uuid 空间）✓ | Ⓑ |
| **行内 Slash 入口（`/`）谁响应** | `JournalFeed` 自己登记一个宿主回调到 `BlockListSlashSlot`（与 `BlockList` 同一注册表、同一 `ensureSlashMenuListId()` 手法）⇒ `BlockView` 不需要知道宿主是谁；菜单本体挂在 `JournalFeed` 的 `Stack` 层（叠在 `List` 之上）✓ | Ⓑ |
| **`callaite_blocksVersion` 刷新** | `JournalFeed` 挂 `@StorageLink('callaite_blocksVersion') @Watch('onBlocksVersionChanged')` ⇒ 重算扁平序列。**并带一个 `equalsRows()` 闸**：序列逐项等价时**不**调 `onDataReloaded()`，避免「打字 ⇒ 整表重建 ⇒ 视口/焦点被打回顶部」（安全依据：行**内容**的刷新由 `BlockView` 自己的 `@Watch` 承担，键未变时它照样重算）✓ | Ⓑ |
| **`embedded` 模式还有别的调用方吗** | **没有** ✓ `git grep -n "embedded"` 全仓：`@Prop embedded` 的**唯一传入点**是 `JournalFeed.ets`；`BlockList` 的构造点只有 `PageView.ets`（不传）与 `JournalFeed.ets`（传 `true`）⇒ 改动后**零调用方** ✓ | Ⓑ |
| **整页模式（文档页）会不会被带偏** | 不会：`BlockList` 的 `List` + `LazyForEach` 分支**一字未改**（只删了它的 `if/else` 外壳）⇒ §3.2 的文档页对照实测 921 节点 / 120.8 MB，与改动前同档 ✓ | Ⓐ |

### 2.3 若只做一半 —— **没有做一半**（并说明为什么不需要）

任务书允许「保留上限但把上限从 30 提到视口行数 + 余量」。**本窗口不采用**，理由：

| 为什么「视口行数 + 余量」不如扁平 `List` | |
|---|---|
| ① **它仍是一个猜出来的常数** ✗ | 「视口行数」随窗口尺寸/分屏/字号变化（本仓有 `callaite_fontSize`）；任何常数都会在某个配置下**要么太小（截断）要么太大（膨胀）** |
| ② **它仍会把「同一节」全量实例化** ✗ | 上限按**节**计，而节是按**天**分的 ⇒ 一天 1037 块时，上限 200 就是 200 行（W6 实测 **209 行 = 261 MB**，>150 MB 预算）✓ |
| ③ **它需要保留截断提示 ⇒ 保留一句会过期的话** ✗ | 提示的计数与真实折叠状态必须同步，多一条状态就多一个漂移面 |
| ④ **扁平 `List` 不引入新常数** ✓ | 实例化行数**由布局引擎决定**（= 视口 + 预取余量），与内容量、窗口尺寸、字号**同时自适应** ✓ |

⇒ 实测支持：**874 节点 / 115.3 MB**，与文档页 **921 节点 / 120.8 MB** **同档** ✓；
且**实例化行数 17/1098**，在 7 节全满的最坏情形下**依然是 17 量级**（因为 item 粒度是块行）✓
