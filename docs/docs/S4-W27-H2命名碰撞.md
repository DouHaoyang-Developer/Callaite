## 0. 一句话结论

**两个入口（`DataStore.createPage` / `DataStore.renamePage`）都在任何副作用之前做「文件名占用」检查，
命中即拒绝并沿 `PageData | undefined` / `boolean` / `OpResult.success` 三层上抛，
组件层用本仓既有的 `promptAction.openToast` 给出可见反馈。**
设备级双向验证通过：**两个入口各拒绝一次，第一个页面的文件 md5 逐字节不变，源页文件也未被删除。**

## 1. 判据设计（全文）

### 1.1 碰撞的精确定义

设 `M(n) = pageNameToFileName(n)` —— **`core/models/Page.ets` 里那一个函数，全仓唯一映射**。

对一次候选操作，新名为 `n`：

- **目标文件** `P = M(n)`
- **已占用集合** `S = { p.filePath | p ∈ indexStore.getAllPages() ∧ p.uuid ≠ targetUuid }`

> **碰撞 ⟺ `P ∈ S`**
> 比较是 **`filePath` 的逐字节、大小写敏感全等**。

### 1.2 为什么占用集合取 `p.filePath` 而不是 `M(p.name)`

写盘那一步是 `joinPath(graphRoot, page.filePath)`（在 `savePage` 内）——
**会被写坏的路径就是 `filePath` 本身**。于是「判据」与「伤害」定义在**同一个项**上，
不发生概念漂移（这正是**陷阱 29**「一个概念两套判据迟早分叉」要防的东西）。

而 `filePath ≡ M(name)` 由构造保证。全仓 `filePath` 只有四个写点，逐个核对均取自同一个 `M`：

| 写点 | 取值 |
|---|---|
| `DataStore.createPage` | `M(name)` |
| `DataStore.renamePage` | `M(newName)` |
| `Page.ets createPageData` | `M(name)` |
| `DataStore.replacePageBlocks` | 原样保留旧 `filePath`（页面名未变） |

⇒ **不存在第二套 sanitize 映射**；`M` 只从 `Page.ets` 取，绝不另写 `sanitizeName`。

### 1.3 自我排除按 uuid，不按名字

- `createPage` —— 没有目标页 ⇒ 排除集为空（**「与自己碰撞」不存在**）。
- `renamePage` —— 排除 `p.uuid === pageUuid`。

**推论（「改大小写/空格算不算改名」的判定）**：
把 `A_B` 改名为 `A:B` 时新旧文件名相同，但那是**同一页**、**没有别的页受损** ⇒ **不算碰撞、放行** ✓。
此时 `renamePage` 是「先删后写同一路径」，`savePage` 随后把内容写回 ⇒ 无损。

⚠️ 调用方本来就有 `renameText !== renamingPage` 的逐字节同名短路（三处），
但**守卫不得依赖它** —— 判据自身必须成立。

### 1.4 大小写：**实测 = 敏感**，判据绝不小写化

设备实测两条：

1. `mount` 输出 `/dev/block/vdd on /data type ext4` ⇒ **ext4 大小写敏感**。
2. 同分区直探：在 `/data/local/tmp` 下 `ZzCase.md`（内容 `A`）与 `zzcase.md`（内容 `B`）**并存**，
   两次 `cat` 分别得 `A` / `B`。

⇒ `M('A_B') = 'A_B.md'` 与 `M('a_b') = 'a_b.md'` 是**两个文件** ⇒ **不构成碰撞**。

> 🔴 **必须避开的陷阱**：`IndexStore.getPageByName` 走 `name.toLowerCase()`，
> **页索引是大小写不敏感的，而文件映射不是**。
> 若图省事复用索引的同一性 ⇒ 会**误拒**（`A_B` 存在就拒绝 `a_b`）。
> **⇒ 本判据绝不做 `toLowerCase()`。**

### 1.5 Unicode：不归一化、逐码元

`M()` 只特判 9 个非法 ASCII（`/ \ : * ? " < > |` → `_`）与 `code < 32`，其余码元原样透传，
**无 NFC/NFD 归一化、无 case folding**。

离线逐行移植 `Page.ets` 的 `M` 实跑（见 §5，脚本落在 `%TEMP%`，不入库）：

| 输入 | `M(input)` | 判定 |
|---|---|---|
| `café`（NFC，U+00E9） | `café.md` | 与下一行**不同串** ⇒ 不碰撞 |
| `cafe` + U+0301（NFD） | `café.md` | 视觉同形但两串不同 ⇒ **两个文件、不碰撞** |
| `中文/页` | `中文_页.md` | 与下一行**同串** ⇒ **碰撞** |
| `中文:页` | `中文_页.md` | **碰撞** |

⇒ **非 ASCII 不豁免**；NFC/NFD 同形名可共存（观感问题，**不是数据丢失**，**登记不修**）。

同一次实跑也**独立复现了 W0 的十变体**：
`A/B A:B A?B A*B A|B A<B A>B A"B A\B A_B` → **1 个不同文件 / 9 个碰撞输入**（都 → `A_B.md`）。
> ⚠️ 这是**离线旁证**，不作为 W0 设备实证的替代。

### 1.6 边界（**只报告，不改**）

| 输入 | `M(input)` | 现状 | W27 处置 |
|---|---|---|---|
| `''` | `_.md` | create 照建；rename **UI 已拦**（三处 `renameText !== ''`） | 不动 |
| `'   '`（三空格） | `'   .md'` | **无人拦** | **刻意放行** —— 它映射到合法且无人占用的文件，按本判据不构成碰撞。**这是有意为之，不是漏掉** ✓ |
| `'\t'` | `_.md` | 控制字符被丢 ⇒ 与 `''` 同文件 | 不动 |
| `'...'` | `Untitled.md` | 不会变隐藏文件 | 不动 |
| `'////'` | `'_______.md'` | 不空 | 不动 |
| `'../etc/passwd'` | `'__etc_passwd.md'` | 穿越已被 `M` neutralise | 不动 |

⇒ **守卫只管碰撞**，不扩大打击面。

### 1.7 两个入口的语义差异

| | `createPage(name, originalName)` | `renamePage(uuid, newName)` |
|---|---|---|
| 排除集 | 空（无目标页） | `{targetUuid}` |
| 命中 | 拒绝，不创建 | 拒绝，**不产生任何副作用** |
| ⚠️ 顺序 | —— | **守卫必须在 `deleteFile(oldPath)` 之前** |

> 🔴 `renamePage` 原实现是「**先删旧文件**，再算新路径」。若把守卫放在删除之后，
> 一次拒绝会把该页变成**盘上无文件** —— 比碰撞本身更糟。
> **设备验收 N2 专门证伪了这一点**：`Z.md` 在拒绝后 md5 逐字节不变（§4.2）。

另注：`rename-page` 这个 op **全仓无生产者**（只有 `OutlinerOps` 定义 + `OutlinerEngine` 分派）
⇒ 目前是死路径；**仍一并修**，避免将来接线时踩坑。

### 1.8 🔴 本裁决**不覆盖**的三项残余（**只登记，不修**）

1. **孤儿文件**：占用集合取自**索引**（已有**页面**对象）。若盘上存在**无对应页对象的孤儿 `.md`**，
   `createPage` / `renamePage` 仍会经 `writeTextSync` 的原子 `renameSync` 覆盖它。
   裁决文字是「另一个已有**页面**」⇒ **孤儿不在范围内**。
   ⚠️ **不要让读者以为守卫覆盖了孤儿**。
2. **`uniquePageName` 的「按名字去重 ≠ 按文件去重」**：
   `components/sidebar/LeftSidebar.ets` 与 `components/common/NewFileDialog.ets` 各有一份
   `uniquePageName`，它按**页索引**（大小写不敏感的名字）去重、**不按文件映射**。
   例如已有页 `A/B` 时，`uniquePageName('A:B')` 认为可用并返回 `A:B`。
   修 H2 后该路径会在 `createPage` 处被拒，**但那个口子本身还在** ✗。
3. **索引层的第二个多对一（「双层键」）—— 与 §1.4 的文件层判据正好相反** ✗✓：
   - **文件层**：`pageNameToFileName` **不做大小写折叠** ⇒ `A_B.md` 与 `a_b.md` 是**两个文件**、**互不碰撞** ✓（§1.4 实测依据）。
   - **索引层**：`IndexStore.addPage` 用 **`page.name.toLowerCase()`** 作 `pageNameIndex` 的键
     ⇒ **`A_B` 与 `a_b` 共用同一个键**，**后建的那一页覆盖前一页的键值** ✗。
   - **后果链** ✓：两页**都**在 `pageMap` 里（`getAllPages()` 两页都在 ✓、文件也各有一份 ✓），
     但 **`getPageByName('A_B')` 会返回「后建的那一页」** ✗ —— 且与**查询串的大小写无关**
     （`getPageByName` 自己也会 `toLowerCase()`，键已被折叠 ⇒ `'A_B'` / `'a_b'` 都命中同一键）。
   - ⇒ **这是「大小写不敏感的名字当身份」与「大小写敏感的文件名当身份」两套概念的分叉** ✗✓
     —— **与陷阱 29 同族**（**同一个概念两套判据迟早分叉** ✓）：分叉不在「映射」上，
     而在**「什么算同一个页面」**上 —— **文件层答「不是同一个」，索引层答「是同一个」** ✓。
   - ⚠️ **与 H2 的关系（别把两者混为一谈）** ✗✓：
     **H2 = 文件层碰撞**（两个名字 → **一个文件** → 覆写丢数据）；
     **本条 = 索引层键碰撞**（两个名字 → **一个查询键** → 查到错的对象）。
     **成因不同、危害面不同、修法也不同** ⇒ **本条只登记，不在本次裁决范围内、未修** ✗。
   - ⚠️ **对本判据的反向约束** ✗✓：**绝不能**因为「索引层不敏感」就把 H2 的碰撞判据也小写化（§1.4）。
     若将来要修本条，**要修的是索引的身份键**（例如文件身份与页名身份分开），**不是 H2 的判据** ✓。
