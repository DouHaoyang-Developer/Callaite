### 1.4 裁决与论证（**两条腿都可用，选 ArkTS 常量**）

> **⚠️ 诚实前提**：本次实测**证伪了「资源可能不生效」的假设** —— 资源腿在全部 4 个取用位上**都生效**，且有编译期名字检查。因此裁决**不能**建立在「资源做不到」之上 ✗。

**裁决 = ArkTS 常量模块**（`entry/src/main/ets/utils/DesignTokens.ets`），**颜色继续走资源**。三条实测/结构性理由：

1. 🔴 **`space:` 这一位是决定性的（实测计数 314 处，是全仓最大的单类取用位）**
   资源腿能让它生效，**但只经由 `ColumnOptionsV2.space?: SpaceType`** —— SDK `column.d.ts:103`，标 **`@since 18`**、`@stagemodelonly`，与既有 314 处使用的 `ColumnOptions.space?: string | number`（`column.d.ts:68`，`@since 7`）**是两个不同的接口**。
   ⇒ 走资源 = 要么**留下第二套写法**（正是 `AGENTS.md` 陷阱 29 的「同一概念两套判据迟早分叉」✗），要么**先把全仓 314 处迁到 V2 形态**（一次与令牌化正交的 API 迁移，自带回归面）。
   ⇒ ArkTS 常量在 V1/V2 两种形态上**都只是 `number`**，零迁移 ✓。

2. 🔴 **图标尺寸这一维资源腿直接缺席（实测 156 处）**
   全仓 **163** 处 `TablerIcon(...)`，其中 **156** 处传**数字字面量**尺寸（14/16/18/20/…共 16 个取值）。而唯一入口 `Icons.ets:128`：
   ```ts
   export function TablerIcon(name: string, size: number = 16, color: ResourceColor = ...)
   ```
   `size` 的类型是 **`number`**，且 `IconRenderer` 对它有**算术**（`:43 return this.iconSize / 12`（线宽）· `:99-101 × densityScale` · `:113 × 0.18`（圆角））。
   ⇒ `Resource` **进不去**（类型错），即便进去也**做不了算术** ⇒ 资源路线在「图标尺寸」这一维上只能空着 ✗。

3. **拼写与算术的同构性**：两腿都有编译期名字检查（实测 ✓），但只有常量腿能参与算术/拼接（`Size.TOUCH_MIN / 2`、`Space.MD * 2`）。

**颜色为什么不一起收进来**：颜色**必须**走资源 —— 明暗两套 49/49 同名令牌靠 `resources/dark/element/` 限定符切换，常量做不到 ✗。
⇒ **最终形态是两条腿各管一件事、零重叠**：**颜色 = 资源** ✓ · **尺寸类 = ArkTS 常量** ✓ —— 不存在「同一概念两套判据」。

**代价（如实登记）** ✗：使用常量需在每个文件加一行 `import`（本窗口 9 个文件各 1 行）；纯 UI 文件无 import 时不能用（本仓无此情形）。

### 3.1 规范 v1（**可执行**）

> **R1**：任何**可点元素**的**命中矩形短边 ≥ 40vp**（= `Size.TOUCH_MIN`）。
> **R2**：视觉尺寸必须更小时，用 `.responseRegion()` 向外扩张 —— **布局与视觉完全不变**。
> **R3（落地手段优先级）**：① 视觉本来就 ≥40 ⇒ 不动；② 视觉可放大且**不产生溢出** ⇒ 直接改尺寸（**优先，因为 `dumpLayout` 可判**）；③ 其余 ⇒ `.responseRegion()`。
> **R4（本窗口新增 —— 密集行降级条款）** ✗✓：**当相邻两个可点控件的间距 < 40vp 时，「两者都 ≥40vp」在几何上不可能**。此时规范降级为：
> **(a)** 各自扩张到**「与相邻控件命中区相切」为止**；
> **(b)** 扩张**以「不重叠」为硬上界** —— 重叠会让点击落到错误控件上，**比热区不足更糟**；
> **(c)** 剩余缺口**必须登记**（不许静默放过）。
> **R5**：**验收用双判据** —— `dumpLayout` 几何（能读到就报）+ **越界点击行为对照**（§3.3 给出配方）。
