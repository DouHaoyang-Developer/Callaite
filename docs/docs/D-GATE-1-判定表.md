## 判据① 整页清空可修

### 真实根因（与 v1.2 的假设不同）
`PLAN-DocumentEditor.md` v1.2 / `EXEC-PLAN.md` 把该缺陷归因为「模式切换重建编辑器、控制器内容为空」，对应修法是「用 markdown 回填」。**实测该归因不成立**（回填早已在 `rebuildSpans()` 里实现，缺陷照旧复现）。真根因在 `LivePreviewHelper.buildSpansInternal()`：

```
if (seg.text === '\n') { currentLineContext = ...; continue; }   // ← 没有 addTextSpan('\n')
```

live 模式**每次 `onDidChange` 都会整表重建 spans**，而重建时**所有换行被丢弃** → 编辑器内容塌成一行 → `handleEditorChange` 把塌缩结果回写 `this.markdown` → 点 ✓ 时 `toMarkdown()` 看到「有一行以 `- ` 开头」就原样返回 → `replacePageBlocks()` 用 **1 个块**覆盖整页并落盘。`DataStore` 的「解析出 0 块就拒绝」闸门挡不住这条路径（塌缩后是 1 块，不是 0 块），这解释了为什么历史记录里既有「块行数 1 → 0」也有「直接变 0 字节」两种表现。

### 复现步骤（修复前，可重复）
1. 新建大纲页，点「整页编辑」→ 切到「源码」模式 → 输入 6 行：
   ```
   - alpha
     - child1
   - beta
   - **bold** text
   - `code` text
   - ==mark== text
   ```
   点 ✓ 重建。磁盘核对：`2026-09-25` 之外的测试页 `未命名 6.md` = **71 B / 6 块**（`  - child1` 的 2 空格缩进也在）。
2. 再次点「整页编辑」（默认进 **实时** 模式）。**不需要输入任何字符**，编辑器即显示为一行：
   `alpha  - child1- betabold text text==mark== text`
   → 证据 `D-GATE-1-证据/01-before-live-整页塌成一行.jpeg`
3. 直接点 ✓。
4. 磁盘核对 → `未命名 6.md` = **66 B / 1 块**：
   `- alpha  - child1- beta- **bold** text- ` + backtick + `code` + backtick + ` text- ==mark== text`
   → **整页 6 块被清空并落盘**。证据 `D-GATE-1-证据/02-before-应用后-1块.jpeg`

（磁盘 0 字节的历史产物仍留在设备上作为旁证：`未命名 4.md` / `未命名 5.md` / `2026-09-19.md` / `2026-09-26.md` 均为 0 B，mtime 2026-09-27 19:25。）

### 修复
1. `LivePreviewHelper.buildSpansInternal()`：`'\n'` 段必须 `controller.addTextSpan('\n')` 后再 `continue`（同时重置行内上下文）。
2. `IntegralEditor.toMarkdown()`：由「只要有一行是块行就整体原样返回」改为**逐行**判定，按「非块行且缩进 ≤ 最近块行 → 补 `- `；缩进更深 → 视为多行块续行」处理，保留缩进。
3. `IntegralEditor.handleEditorChange()`：新增「结构塌缩」防护 —— 多行 `markdown` 不得被单行的提取结果覆盖。
4. `IntegralEditor.applyAndRebuild()`：新增硬闸 2 —— 原页面多块而待写入文本仅一行时直接拒绝（与 `DataStore` 的「0 块」闸门互补）。

### 复测（修复后）
测试页 `2026-09-25`（16 块）：

| 步骤 | 磁盘 |
|---|---|
| 修复前基线（本轮实验开始前） | 415 B · md5 `5e54445a363e5d9f8e2dafb366c28f36` |
| 「整页编辑」→ 实时模式 | 编辑器显示 **16 行**（不再塌成一行）→ `D-GATE-1-证据/04-after-live-16行.md5不变.jpeg` |
| 点 ✓ | **415 B · md5 `5e54445a363e5d9f8e2dafb366c28f36`（逐字节不变）** |

日志：`[IntegralEditor] loaded page=2026-09-25 blocks=16 mdLen=255`；无 `LivePreviewHelper buildSpans error`。

## 判据② 分屏空白可修

### 复现步骤（修复前）
1. 打开 `未命名 6`（此刻已被①的缺陷毁成 1 块）。
2. 「整页编辑」→ 点「分屏」。
3. 观察：**左栏不是空白，但内容是塌缩后的一行**（`alpha  - child1- beta- bold text-  text-==mark== text`，无换行、无缩进）。
   → 证据 `D-GATE-1-证据/03-before-分屏左栏塌缩.jpeg`

**「左栏完全空白」这一形态在现版本上未能复现** —— 因为 `rebuildSpans()` 里的 `extractText() !== '' ? extracted : this.markdown` 回填早已存在（源码注释记录了「原先漏了，导致分屏左栏空白」）。也就是说：**② 的「回填」部分此前已修好，残留的是「内容正确性」部分，其根因与①完全相同。**

### 修复
- 左栏：即①的换行修复 + 回填（`getSpans()` 读回的 span 值**逐字**包含 `- ` 前缀与每级 2 空格缩进，故缩进天然还原，无需另建缩进映射）。
- 右栏：`PreviewPane` 的 `ForEach` key 由 `line.text + line.size` 改为 `line.id`（新增 `PreviewLine.id`）。原 key 在内容重复的行上重复，ArkUI 直接报
  `FIX THIS APPLICATION ERROR: @Component 'IntegralEditor'[2075]: Ids generated by the ForEach id gen function must be unique. ... Duplicated index: [1..15]`
  并**只渲染 16 行中的 1 行**。

### 复测（修复后）
`2026-09-25` → 整页编辑 → 分屏：
- 左栏：16 行全部显示（缩进/前缀正确，live 样式生效）
- 右栏：16 条 preview 行全部显示（修复前只有 1 条）
- 状态栏：`16 块 · 64 字`
→ 证据 `D-GATE-1-证据/05-after-分屏-两栏完整.jpeg`；日志无 `FIX THIS APPLICATION ERROR`。

**缩进的直接验证**：修复前用 6 行示例（含 `  - child1`）在源码模式点 ✓ 后，磁盘文件为 71 B 且第 2 行为 `  - child1`（2 空格缩进原样落盘），证明 `getSpans()` 往返保缩进；live 模式因①的缺陷当时无法用于该验证（现已修复）。

## 判据③ 三类 span 编辑态↔渲染态动态翻转

### 修复前的真实状态：**不只是"没实现"，而是会崩**
1. **高亮 `==x==` 完全未实现**：`MarkdownSegmenter` 的 `specials` 里没有 `=`，`==mark==` 整体被当作正文，标记始终可见、无任何渲染样式。
2. **行内代码 `` `x` `` 内容不可见**：分词器把**整段（含内容）**标为 `syntax`，而 live 规则是「光标不在语法段内就隐藏」→ 单词 `code` 从页面上消失。
   → 证据 `D-GATE-1-证据/12-before-行内代码内容不可见.png`
3. **加粗内容不加粗**：标记能隐藏，但内容走 `contentStyle()`（常规字重），渲染态与编辑态视觉上无区别。
4. **致命项**：live 模式下把光标移进任一标记，即触发 `LivePreviewHelper buildSpans error at buildSpansInternal code=undefined msg=Stack overflow!`，编辑器被 `deleteSpans()` 清空且未回填 → **整页空白**（100% 复现）。

第 4 项的根因（**既有缺陷，非本次引入**）：`rebuildSpans()` 末尾调用 `setCaretOffset(caret)`，该调用会**同步**回调 `onSelectionChange`；此时方法内快照（`lastSpanCaret`）尚未写入，`handleSelectionChange` 判定「光标变了」→ 再次 `rebuildSpans()` → 无限同步递归，4~5 层后爆栈。既有的 `livePreview.getIsRebuilding()` 闸门在 `setCaretOffset` 阶段已经放开，挡不住。日志实证：200 ms 内 `buildSpansInternal` 完整跑完 4 轮后在**第 5 轮入口**爆栈。

### 修复
1. `MarkdownSegmenter.parseInlineMarkdown()`：
   - 新增高亮 `==`：`==`(syntax) + 内容(content) + `==`(syntax)；`specials` 加入 `=`。
   - 行内代码拆成 `` ` ``(syntax) + 内容(content) + `` ` ``(syntax)。
   - 新增兜底推进：`specials` 中的字符若无分支接手（孤立的 `!`、未成对的 `=`）必须消费 1 个字符，否则外层 `while` **永不退出**（挂死主线程）。
2. `LivePreviewHelper`：
   - `buildSpansInternal()` 维护 `inBold / inInlineCode / inHighlight` 行内上下文，标记段按 `cursorInside` 在「显形(灰) / 隐藏(透明)」间切换，内容段据此选渲染样式。
   - 新增三种渲染态样式：加粗（Bold）、行内代码（`app.color.inline_code` + 弱底色）、高亮（**`RichEditorTextStyle.textBackgroundStyle`，@since 18** → 真·底色填充，色值 `app.color.search_highlight`）。
   - `syntaxHiddenStyle()` 由 `fontSize: 1` 改为与显形态**同字号同字体、仅颜色透明**（同度量翻转，避免翻转引发重排反馈）。
   - 错误日志由 `JSON.stringify(e)`（恒为 `{}`）改为打印 `stage/code/message`，可直接定位是 `deleteSpans` 还是 `buildSpansInternal` 抛错。
3. `IntegralEditor.rebuildSpans()`：新增 `isRebuildingSpans` 重入闸，覆盖**整个方法**（含 `setCaretOffset` 的同步回调窗口），并把快照写在 `setCaretOffset` **之前**；`handleEditorChange` / `handleSelectionChange` 增加「文本/光标未变则不重建」短路。

### 复测（修复后，逐项目视）
| 类别 | 编辑态（光标在标记内） | 渲染态（光标在别处） |
|---|---|---|
| 加粗 `**bold**` | `**` 显形（灰），光标停在标记后 → `07-c3-加粗-编辑态.png` | `**` 消失、`bold` 粗体 → `06-c3-渲染态-三类样式.png`；离开后恢复渲染态 → `08-c3-加粗-离开后恢复渲染态.png` |
| 行内代码 `` `code` `` | 反引号显形 → `09-c3-行内代码-编辑态.png` | 反引号消失、`code` 呈代码色 + 弱底色（**修复前该词整体不可见**） |
| 高亮 `==mark==` | `==` 显形 → `10-c3-高亮-编辑态.png` | `==` 消失、`mark` 带**黄色底色块**（`textBackgroundStyle`） |

全程：光标始终可见且停在点击处，编辑器未再出现空白，日志无 `Stack overflow!`。三类走的是**同一个标记分支 + 同一套上下文变量**，代码级同源。

## 判据④ IME 中文组词无损（W2）

> **口径（既定裁决）**：模拟器软键盘「初判」即可；**物理键盘终验留 Phase 2**。故本判据**必须分两栏**，**不得把初判写成终验通过**。

### 装置与前提
- 装置：同 W1（平板模拟器 `MatePad Pro 13`，API 26），系统 IME = `com.huawei.hmos.inputmethod`；被测对象 = `IntegralEditor`（原生 `RichEditor`）**实时（live）**模式，页面 `2026-09-25`（16 块）。
- **关键前提（保证实验零副作用）**：`IntegralEditor` **不自动落盘** —— 只有点 ✓（`applyAndRebuild()`）才会 `replacePageBlocks` + `markDirty`。因此组词/上屏全过程 `2026-09-25.md` 的 md5 **恒为 `5e54445a363e5d9f8e2dafb366c28f36`**（与 W1 基线逐字节相同，实验前后各核对一次）。
- 证据等级：**Ⓐ 真实 UI 操作**（软键盘逐键点击 + 候选条/编辑器截图目视），辅以 **Ⓑ 代码级论证**。
