## 2. 定位（「哪条路径 × 什么输入 ⇒ 多大停顿」）

### 2.1 对症根因 ①：`ContentRenderer.findPatternStarts` 的 Θ(n²) 后缀重扫

`ContentRenderer.parse`（块视图逐块调用，`BlockView.ets:245`）的主循环在 `tryMatchAt` 失败时调用
`findPatternStarts(text, pos)` —— 该函数**从 `pos` 一直扫到文末**，把**每一个**候补下标 `push` 进数组；而调用点**只用 `candidates[0]`** ✗。

⇒ 当文本里连续出现「**是模式起始字符、却因缺闭合定界符无法成段**」的字符时（`!` / `=` / `*` / `[` / `(` / `~` / `#` / `$`），`tryMatchAt` 每次都失败、`pos` 每次只前进 1，于是「扫到文末 + 建一个长数组」被**重复 n 次** ⇒ **Θ(n²) 时间 + Θ(n²) 分配**（总 `push` 次数 ≈ n²/2）。

- **触发输入**：任意一个块里出现**长串同一种标记字符**。`!`×8000 即 7592 ms；20 KB 即 ≥3 s（系统已报 `THREAD_BLOCK_3S`）。
- **栈顶语义吻合** ✓：全程 `text.charAt(i)` 逐字符 + 数组增长（拷贝），与历史 fault 的 `BuiltinStub_StringCharAtStwCopy`（逐字符 + 拷贝）一致。
- **证据等级**：Ⓐ 设备实测（剂量-反应 + 函数计时）✓

### 2.2 对症根因 ②：分段器「按字符产出段」⇒ 下游每段一次重活

两个分段器在**无法成段**时都是**逐字符各推一个段**：

| 路径 | 段去向 | 每段的下游成本（本窗口实测） |
|---|---|---|
| `ContentRenderer.parse` → `BlockView.displaySegments` | `ForEach` **逐段建一个组件**（`BlockView.ets:605`） | **≈0.54 ms/段**（8000 段 ⇒ 单次停顿里多出 ≈4.3 s） |
| `parseMarkdownSegments` → `LivePreviewHelper.buildSpansInternal` | **逐段调一次** `controller.addTextSpan()`（`LivePreviewHelper.ets:392`） | **≈1.28 ms/段**（4000 段 ⇒ `buildSpans` **5130 ms**） |

⇒ 段数**与输入字符数同阶且没有上界** ⇒ 这两条路的停顿同样没有上界。`addTextSpan` 那条正是历史 ANR 的**同一条栈**（`ArkUIAceContainerNonPointerEvent` / RichEditor 事件路径）✓。

- **触发输入**：`!`×4000 单块 ⇒ 整页编辑器 live 模式 **5595 ms**。
- **注意**：这条与 §2.1 是**独立**的两件事 —— 即使把 ①的 Θ(n²) 去掉，段爆炸仍在（见 §3.2 的实测：只做①②③时 20 KB 仍触发 `THREAD_BLOCK_3S`）。**必须两条都修** ✓。

### 3.2 为什么恰好是这三处（20 KB 的教训）

只做 ①②③ 时，**20 KB 的 `!` 单块仍触发系统 `THREAD_BLOCK_3S`**（`dumpLayout` 报 `Get window nodes failed`）。
把 4000 → 8000 的剂量-反应曲线（912 → 3265，×3.58）逐项拆掉之后仍剩下与字符数同阶的成本，指向兜底分支里**每字符一次 `substring`**：
若运行时的 `substring` 是**整串拷贝**而非引用切片，这就是又一次 Θ(n²) —— 与 `StringCharAtStwCopy` 的「逐字符 + 拷贝」语义吻合 ✓。
补上 **①b** 后同一输入不再触发 ✓。**这正好说明「只修最显眼的那一处」是不够的**。

### 3.3 为什么这是最小改动、为什么不引入新风险

**改动形状**：只在两处「**产出段**」的地方收口 —— ①只找第一个候补（少做无用功），①b/②/③把**相邻同类段合并**。**没有任何调用方、回调、状态机、落盘路径被改动** ✓。

**行为等价的四条论证**：
1. **①**：`findPatternStarts(...).length > 0` ⇔ `findFirstPatternStart(...) >= 0`，且 `candidates[0] === findFirstPatternStart(...)` —— 旧代码**只读 `[0]`** ⇒ 输出逐字节不变 ✓
2. **①b/②**：TEXT 段在 `BlockView.RenderSegment` 里走**同一个 `Text(seg.text)` 分支**，`isClickable(TEXT) === false`；拆 N 段与并 1 段在同一 `Text` 内相邻字符**无额外间距** ⇒ 渲染相同；各段文本**拼接仍逐字符等于原文本** ⇒ 不引入/不丢失字符 ✓
3. **③**：`buildSpansInternal` / `buildSourceSpans` 的状态机**只由 syntax 段的确切文本**（`'**'` / `` '`' `` / `'=='` / `'\n'` / 行首正则）驱动；**content 段不参与任何状态迁移**。两个相邻 content 段之间**不存在状态差**（样式由 `inBold` / `inInlineCode` / `inHighlight` / 行上下文决定，这三者只被 syntax 段与换行翻转）⇒ 并成一段后样式与文本逐字符一致 ✓
4. **③ 刻意不合并 syntax 段**：`'**'` 与 `'***'` 合并会破坏 `seg.text === '**'` 的**翻转判据** ✗ —— 这是本函数只处理 content 的原因 ✓

**合并实现本身不引入新复杂度**：用 `buf.push(...)` + `join('')`，**不是**逐次 `prev + seg.text` —— 后者本身就是 Θ(n²) 拼接（本窗口已实测该形状，故不再复制）✓

**两条独立验证**（见 §4.2、§4.3）：
- **差分等价测试**：149 例语料（病态 + 正常 + 随机 Markdown）× {拼接文本、逐字符样式序列（5 个光标位）、逐字符段类型/extra} ⇒ **0 处不一致** ✓
- **真实夹具逐像素比对**：298 块页面块视图截图，改前 vs 改后**差异像素 772 / 5,529,600，且全部落在状态栏时钟区**；**排除时钟后 = 0** ✓
