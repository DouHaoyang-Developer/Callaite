## 1. 任务 0：`IntegralEditor` live 编辑不落盘（数据丢失）

### 1.1 复核到的根因（与 W1 §4.3 一致，本窗口独立复现）

- 唯一写盘路径 `applyAndRebuild()`（`IntegralEditor.ets`）**只由顶部 ✓ 按钮调用**；
- `handleEditorChange()` 只把编辑器文本写进内存副本 `this.markdown`，**没有任何落盘动作**；
- 于是「切模式 / 切页 / `LazyForEach` 回收」销毁 `RichEditor` ⇒ 未点 ✓ 的输入不可恢复地丢失。

### 1.2 修法

| 位置 | 改动 |
|---|---|
| `IntegralEditor.handleEditorChange()` | 判定「这是一次真实文本变更」之后：`isDirty = true` + **重新武装 800ms 防抖计时器** |
| `IntegralEditor.flushSave()`（新增） | 读回编辑器文本 → `toMarkdown()` → **复用既有的两道防误删硬闸**（空内容 / 结构塌缩）→ `ws.replacePageBlocks()` → `SaveQueue.markDirty()` |
| `IntegralEditor.aboutToDisappear()`（新增） | `flushSave()` + `DirtyPageTracker.flushNow()` 收尾 |
| `isDirty` / `lastSavedText` | 为什么不用「字符串比较判脏」：本组件的两道容错闸门会让 `this.markdown` 与编辑器文本**合法地不一致**，拿它当「上次已存内容」会误报，进而**每次按键都触发一次整页重建** |

**为什么不引入 ANR 风险**（逐条对应历史 ANR 的两条线索）：

1. **不改变 span 重建路径的任何一行。** `rebuildSpans` 的输入、调用点、复杂度全部不动。
2. **历史 ANR 的成因不是扫描成本** —— 那份 fault 报告发生在 **1 个块 / 66 字节**的页面上（W1 §1.5 已证）。
3. **单次成本 = 与「点一次 ✓ 按钮」完全等价**（`toMarkdown` 切行 + 整页解析 + 写盘），不是一个新量级的工作。真正的风险是「每次按键都跑一遍」⇒ **800ms 防抖**把它压成「连续输入只触发一次」。
4. **比 `WebEditor` 的既有 autosave 更省**：WebEditor 在每次按键的 `onDidChange` 上直接跑 `updateBlockContent`；本实现连那一步都合并掉了。
5. **兜底不变**：成功 ⇒ 走既有 `DirtyPageTracker`（失焦 / 切页 / 结构操作 / **5s 硬截止**）；`aboutToDisappear` 另做一次收尾 flush。

### 2.2 三条硬要求的落地位置

| 硬要求 | 落地 | 说明 |
|---|---|---|
| **① 回填闸** | `beginProgrammaticUpdate()` / `endProgrammaticUpdate()`（闸门深度）+ `snapshotText` 二次拦 | 所有程序化改文本的路径（`onReady` 首填、重建、工具条命令）都入闸；闸门落下后的**迟到回调**再按「文本与快照逐字符相同」丢弃 ⇒ **不依赖时序假设**，同时避免退化成「每次按键都重建」 |
| **② 销毁前四步** | `aboutToDisappear()` | ⓪ 释放排程 → ① 读回文本 → ② 与 `BlockData.content` 比对、**不同才写**（走 `EditorService.updateBlockContent`，与 `NativeBridge` 同构）→ ③ `DirtyPageTracker.flushNow()` → ④ 清 span + 置空本地引用 |
| **③ `caretOffset` 块内相对** | `onSelectionChange`（`getCaretOffset()`）/ `onDidChange`（`rangeAfter.end`） | 控制器的坐标原点就是本块第 0 个字符 ⇒ 天然块内相对。**绝不能**沿用整页绝对 offset：那样第一个块之后的任何位置都会判成「不在任何段内」，`**`/`` ` ``/`==` 的标记**永不显示** |

**焦点**：权威 = `EditorService.focusedBlockUuid`（镜像 `callaite_focusedBlock`）；
`BlockEditor` 用 `@StorageLink` 读它，**只在「本块就是权威焦点块」时** `focusControl.requestFocus('.id()')`，
`onFocus`/`onBlur` **只上报不改写焦点**（防回环）。请求放在 `onReady` 之后的**下一帧**（`setTimeout(…, 0)`），
接受它是异步的（实测请求 → `onFocus` ≈620ms，见 W1 §2.3）。

### 2.3 A-0（块内整块重建）+ 围栏播种

- **A-0**：`deleteSpans()`（无参，只作用于本实例）+ 对本块 `parseMarkdownSegments` + 逐段 `addTextSpan`。
  **A-1 刻意不做**（块内段数是个位数，增量与整块的实际收益差在微秒级，却引入「段数组 ↔ 字符 offset 表」这一新的可错状态）。
- **围栏播种**：`FenceOpenCache` 顺序扫**可见行序列**（与 `BlockList` 同一实现 `getVisibleBlocks`），
  为每个块记下「进入它之前的围栏状态」；`buildSpans(…, codeBlockOpen)` 据此播种。
  播种为 true 时在最前面补一个 `\n` 跨度，使「spans 之和」**逐字符等于**块内容
  —— 否则销毁前的「读回 vs `BlockData.content`」比对会凭空多/少一个换行，每次销毁都误判为「内容变了」。
- **缓存键**：`pageUuid + 可见行数 + 各行 uuid 的滚动 hash`。
  结构性变更 ⇒ 签名变 ⇒ 自动失效；**文本输入 ⇒ 签名不变 ⇒ 零重算**。
  比「挂 `callaite_blocksVersion`」更稳：不需要调用方记得 bump，也不会因无关页面的 bump 而失效。
- **块内状态起点**（U1 已裁决「接受」）：`currentLineContext`/`headingLevel` 从 `NORMAL`/0 起步；
  `inBold`/`inInlineCode`/`inHighlight` 从 `false` 起步 ⇒ 未闭合标记不再跨块溢出。

### 3.1 两处设计文档标注「需复核」的

**(U2) `RichEditor` 对按键的消费面（vs W12 快捷键重排）**

- **结构层面（Ⓑ）**：`BlockEditor` **不注册任何按键处理器**（无 `onKeyEvent` / `onKeyPreIme` / `onKeyEventDispatch`），
  因此 **不可能新增**任何按键消费。改造前 `WebEditor`（HTML 内 `keydown` 拦截后经桥回传）与今天 `RichEditor`
  的 Enter/Tab/Backspace 归属**都在应用侧**，且判据（`ContentArea` 的 `onKeyEvent` / `onKeyPreIme` →
  `ShortcutService` / `OverlayKeyRouter`）**一行未改** ⇒ 结构性回归不可能。
- **未实测（✗）**：`RichEditor` 是否会在 ArkUI 之前吞掉部分导航键（方向键 / Esc），
  从而让部分快捷键变成「原生编辑行为」。给出「按键归属表」需要对
  `Tab` / `Shift+Tab` / `Enter` / `↑↓` / `Ctrl+Z` 逐个注入并观察**编辑器内容 vs 数据变化**，
  而本设备的注入键与真实键盘路径存在已知差异（见 §4.3）⇒ **登记为待实测**，不写成通过。

**(U3) `OverlayKeyRouter` 的组词守卫对原生 `RichEditor` 是否成立（vs W11-U2.2）**

- **结构层面（Ⓑ）**：`OverlayKeyRouter.ets` / `ShortcutService.ets` / 各浮层文件**零改动**。
  路由器的三条硬约束未变，其中最关键的一条是「**只在 overlayOpen 态路由**：
  没有任何浮层打开时 `handle()` 恒返回 false」⇒ 纯块编辑（无浮层）时**一个键都不经过路由器**。
- **设计分层（Ⓑ）**：回车/blur 之前就被排除在路由器之外（`isNavKey` 只含 ↑↓/esc，刻意排除回车），
  回车的正确入口是 `TextInput.onSubmit` —— 该结论与「编辑器是 WebView 还是原生 `RichEditor`」**正交**。
- **未验证（✗）**：`isImeComposing()` 的读取通道是 `TextInput.onChange` 的第二实参 `previewText`，
  而**原生 `RichEditor` 没有对应的 onChange 通道**（`RichEditor` 的 `aboutToIMEInput` / `onDidChange`
  都不投递 `previewText`）⇒ 若将来把浮层的输入框换到 `RichEditor`，这条兜底守卫会**静默失效**。
  本窗口**没有**做这个替换 ⇒ 当前不受影响，但**登记为后续约束**。
  当台设备的**组词态 A/B 对照未能复现**（见 §4.3）⇒ 组词回归**未验证**。

## 5. Checkpoint A 核算（W2 尾，如实）

### 5.1 ① 前置 A 实际成本 ≤ 2 窗口？

**满足 ✓。** 实际成本 = **1 个窗口（W2）**：

- 设计（W1）已把范围收窄为 **A-0 单块内整块重建** ⇒ 落地只需「`deleteSpans` + 本块 `parseMarkdownSegments` + 逐段 `addTextSpan`」，
  与 `LivePreviewHelper` 既有代码形状几乎一致，只把 `text` 从「全页」换成「本块」；
- 唯一外挂的一层是**围栏播种**（`inCodeBlock` 是迁移前唯一的跨块传播项），用一个页面级缓存 + 一个可选参数解决；
- **A-1（块内脏段增量）实测不需要**：块内段数是个位数，整块重建的单次成本已经与「一次 span 写回」同量级。

### 5.2 ② 长文档连续输入 ANR 消除？

**不满足 ✗ —— 如实登记，并触发回切评估。**

理由（三条，缺一不可）：

1. **历史 ANR 的触发条件至今未被复现。** W1 的 298 行 × 70 键实验里 70/70 成功、单键中位 222.8ms、
   无 >500ms、系统日志无新 `appfreeze`（设计文档 §4.2）。**没有复现过的缺陷，不能宣称已修。**
2. **「按块缩小重建范围」在原理上不可能是那个 ANR 的解。** 历史 fault 报告发生在
   **1 个块 / 66 字节**的页面上（`Reason=THREAD_BLOCK_6S`，主线程阻塞 ≈4555ms，
   栈顶 `BuiltinStub_StringCharAtStwCopy`）——66 字节的页面上不存在「扫全文慢」这回事。
   B 形态降低的是**平均**单键成本，不消除**单次调用的无界停顿**（设计文档 §1.5 / A-2）。
3. **本窗口的 A-0 也没有针对无界停顿做任何事。** `rebuildSpans` 内部仍是「一条同步长任务」；
   A-0/A-1 都不修这个（设计文档 §1.4 已写明）。

⇒ **按冲刺明文「任一不满足 ⇒ 停下走回切评估（v2.2 §15.4 触发器②）」**：建议把省下的预算转投
**A-2（给解析/重建加上界与让出）** 与**病态输入压力测试**，而不是继续在「缩小扫描范围」上加码。

### 5.3 顺带确认的收益（不改判 5.2 的结论）

- 结构上，「单键触发全页 span 重建」这条路径在**块视图**里已经不存在：`BlockEditor.onDidChange`
  只在**本块**上重建（`O(该块段数)`），且由 `lastSpanText` 短路保证一次变更只重建一次。
- 但**整页编辑器（`IntegralEditor` live）仍然保留全页重建**（本次刻意不动它的重建路径，
  以免把「数据丢失修复」与「性能改造」两件事混在一起）⇒ 长文档在整页编辑器里输入时，
  单键成本仍是 `O(全页段数)`。

## 7. 不可自证项（如实）
