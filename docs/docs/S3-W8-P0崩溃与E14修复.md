### 2.2 实际改法（对症）

`entry/src/main/ets/utils/MarkdownSegmenter.ets` —— **`parseInlineMarkdown` 的 wikilink 分支**：

**根因（与 W7 一致，已由 §1 独立复现）**：`text.startsWith('[[')` **没有 position 实参 = 只看串首**，
而 `i` 是**游标** ⇒ 「文本以 `[[` 开头、且首个 `]]` 之后还有字符」时 `i` 被写回一个**已经走过**的位置 ⇒ **不前进** ✓。

**修法（关键**不是**改判定语义，而是加一条「不许把游标写回去」的守卫）**：

```ts
const wikiClose: number = text.startsWith('[[') ? text.indexOf(']]', 2) : -1;
const isWikiTail: boolean = wikiClose !== -1 && wikiClose + 2 <= i;
if (!isWikiTail && text.startsWith('[[')) {
  const closeIdx = wikiClose;
  ...
}
```

**为什么这条是零漂移的（可证）**：
`startsWith`（无实参）是**全局属性**、与游标无关 ⇒ 它**恒等价于** `i === 0 && startsWith('[[')`。
所以「分支进入但会把 `i` 写回去」的**充要条件**就是 `closeIdx + 2 <= i` ⇒ 守卫**恰好**只拦这一种情形 ✓。
⇒ 对**所有修复前能正常终止的输入**，该守卫**恒假** ⇒ 分段结果**逐字节不变** ✓。

**同时刻意保留**：
- `indexOf(']]', 2)` 与 `slice(2, closeIdx)` **一字未动** ⇒ 与守卫配合后二者等价于 `i+2`（因为守卫保证了此刻 `i === 0`）✓；
- 「未闭合 `[[` ⇒ 逐字符当 content」通道**一字未动**（`closeIdx === -1` 时没有越界风险）✓ ——
  ⚠️ 这一条我**踩过一次**：只写 `i === 0` 守卫会让**未闭合**输入也跳过该分支，实测 **30 条漂移** ✗ ⇒ 已改回 `isWikiTail` 判据 ✓。

### 2.3 **无条件前进兜底**（防的是「类」，不是这一个 bug）

`parseInlineMarkdown` 的 `while` 循环**末尾**新增水位守卫：

```ts
let guardMark = -1;
let guardFires = 0;
while (i < text.length) {
  ... // 全部分支（除最后一段外都带 continue，且 continue 之前都写了 i =/i +=）
  if (i <= guardMark) {                    // ← 本迭代没有前进
    guardFires += 1;
    hilog.warn(..., 'parseInlineMarkdown cursor stalled: forced advance i=%d len=%d fires=%d',
      i, text.length, guardFires);
    i = guardMark + 1;                     // ← 强制前进
  }
  guardMark = i;
}
```

**设计要点（逐条有据）**：
1. **位置选在「循环体末尾」** ⇒ 只有**会回到循环条件**的路径才经过它；带 `continue` 的分支**跳过**它。
   这不是漏洞：那些分支的 `continue` 之前**都**写了 `i =`/`i +=`（§3 逐分支核对），所以不会漏 ✓。
2. **`i <= guardMark`（而非 `<`）** ⇒ 第一次迭代（`guardMark = -1`, `i = 0`）不会误判 ✓。
3. **只在真发生时打一条 WARN + 计数** ⇒ 兼作「**还有没有第三个不推进的分支**」的**活体探针** ✓
   （W7 只能用离线探针猜；这条守卫让真机上也能一句话证伪 ✓）。
4. **兜底语义与仓内既有先例一致** ✓：`ContentRenderer.parse`（渲染态那一个解析器）早就有**同类兜底**
   （`ContentRenderer.ets:117-129`，注释自称「P0 死循环兜底（既有缺陷，非本次引入）」，
   归因 `e5fc508`）—— 那次是**逐字消费一个字符**。本窗口把这条约定**补齐到编辑态解析器** ✓。
   > 仓里因此形成一条可复用判据：**游标式 while 必须有无条件前进兜底** ✓（写在 AGENTS 陷阱 37 的建议里）。

## 3. ⚠️ **同函数内是否还有别的「分支不推进」**（逐分支分析 —— 本窗口最有价值的附加产出）

方法：`parseInlineMarkdown` 的终止性完全依赖**每次迭代 `i` 严格增长**这条不变量；
逐个分支把它形式化（`i'` = 该分支执行后的游标），**只有能证明 `i' ≥ i+1` 才算安全** ✓。

| # | 分支（行号=修复后） | 进入条件 | 出口游标 `i'` | `i' ≥ i+1`？ | 结论 |
|---|---|---|---|---|---|
| 1 | 行内 LaTeX `$…$` | `charAt(i)==='$'` 且非 `$$` | `end+1`（`end>i+1`）或 `i+1` | ✅ | 安全 |
| 2 | 粗斜体 `***` | `startsWith('***', i)` —— ⚠️ **带 position 实参** ✓ | `end+3`（`end>i+3`）或 `i+3` | ✅ | 安全（**≥3**） |
| 3 | 粗体 `**` | `startsWith('**', i)` —— ⚠️ **带 position** ✓ | `end+2`（`end>i+2`）或 `i+2` | ✅ | 安全（**≥2**） |
| 4 | 斜体 `*` | `charAt(i)==='*'` 且非 `**` | `end+1`（`end>i+1`）或 `i+1` | ✅ | 安全 |
| 5 | 高亮 `==` | `startsWith('==', i)` —— ⚠️ **带 position** ✓ | `end+2`（`end>i+2`）；未闭合走 `i+1` | ✅ | 安全 |
| 6 | 行内代码 `` ` `` | `charAt(i)==='`'` | `end+1`（`end>i`）；无闭合走 `i+1` | ✅ | 安全 |
| 7 | **Wiki `[[`** | **`startsWith('[[')` —— ✗ 无 position** | **`closeIdx+2`，可 ≤ `i`** | **✗** | **本次修掉** ✓ |
| 8 | 链接 `[t](u)` | `charAt(i)==='['` | `closeParen+1`；`closeBracket` 起点 `i` ⇒ `>i` ⇒ `closeParen≥i+2` 或 `-1` ⇒ 走 `i+1` | ✅ | 安全（**判据 `closeParen > closeBracket` 本身就把 `-1` 排除了**）|
| 9 | 图片 `![t](u)` | `charAt(i)==='!'` 且 `charAt(i+1)==='['` | `closeParen+1`（`≥i+1`）；否则 `i+1` | ✅ | 安全 |
| 10 | 普通字符块 | 落到 `specials` 扫描 | `nextSpecials` 严格递增；`chunk` 非空 ⇒ `continue` | ✅ | 安全 |
| 11 | **最终兜底**（既有） | `chunk` 为空且 `i` 未动 | `i+1` | ✅ | 安全（`d4d1b5f` 修的第 1 例）|

**结论** ✗✓：**同函数内没有第二个「不推进」分支** ✓ ——
**唯一的破口就是 #7**，而它已修 ✓。
⚠️ **但这条结论只在当下成立**：函数里已经有**两例**同族缺陷（#11 由 `d4d1b5f`、#7 由本窗口），
⇒ **不变量本身必须落成代码**（§2.3 的兜底）而不是靠「每次都逐分支证明」✗✓。

**关于 `parseMarkdownSegments`（外层）**：它的循环是
`for (let i = 0; i < lines.length; i++)` —— **`for` 的增量表达式保证推进** ✓，
且每个分支的 `continue` 都回到该 `for`（无嵌套 while）⇒ **结构上不可能不推进** ✓。
> 顺带核实一条**不是**缺陷的观察：`calloutMatch[2]?.length` 用了可选链，
> 但该正则的第 2 组 `(.*)` **永远匹配**（可为空串）⇒ 可选链恒不生效，属**冗余但无害** ✓（未改动 ✓）。

**另：全仓只有一处「无 position 的 `startsWith('[[…')`」** ✓ ——
`git grep` 全 `ets/` 只命中本文件（另两处是注释）✓；编辑态的孪生解析器
