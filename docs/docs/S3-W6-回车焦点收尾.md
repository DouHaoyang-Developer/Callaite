## 2. 根因（**明确结论**）：两个缺陷叠加

### 2.1 缺陷一 🔴：`insert-block` 之后**视图层从未被通知**（真根因）

**机制（Ⓑ 代码级，已核实）**：

- `EditorService.createBlockBelow()` → `ws.executeOp({type:'insert-block', …})` → `OutlinerEngine.execute()`
  → `dispatch(op)` → `doInsertBlock()` → `persistForOp()` 落盘。
- **`OutlinerEngine` 内 `bumpBlocksVersion` / `AppState` 命中数 = 0**（`git grep` 在 `core/engine/` 下 **0 命中**）。
- 全仓 `AppState.bumpBlocksVersion()` 调用点全在 **UI 组件侧**（`BlockView`/`BlockSelection`/`BlockDragLayer`/`PropertyEditor`/`PropertyConfig`/`BlockAnchorService`）。
  ⇒ 这是本仓一条**既有的、未成文的分工**：引擎负责数据与磁盘，**bump 由调用它的 UI 负责**。
  而 `createBlockBelow` 的调用方是 `BlockEditor`（`routeKeyEnter`），**它没有 bump**。
- `BlockList` 的刷新入口**只有两个**：`aboutToAppear()` 与 `@StorageLink('callaite_blocksVersion') @Watch('onBlocksVersionChanged')`。
  两者都不触发 ⇒ `refreshBlocks()` 不跑 ⇒ `this.dataSource.setBlocks(this.rows)` 不被调用
  ⇒ `BlockDataSource.onDataReloaded()` 不广播 ⇒ **`LazyForEach` 不会重建行序列**。

**Ⓒ 探针证据（决定性：一条日志的「缺席」）**：

**关键读数（三条）**：

1. `BL.refresh` 在 16:09:33 **一次都没有出现** ⇒ 视图层确实没被通知（缺陷一）。
2. `BV.watch` 命中 **34 个** `self`，**其中没有 `93974e59`** ⇒ **新块那一行的 `BlockView` 从未被创建**。
3. `BE.appear` 全会话 **1 次**，且是旧行（点击时创建的那次）⇒ **新块的 `BlockEditor` 从未挂载过**。

⇒ **W5 §6.1 的猜测得到了确认与修正**：
W5 说「高度怀疑新行根本没进编辑态」—— 方向对 ✓，但**层级差一步**：
不是「行进了编辑态却没拿到焦点」，而是**「行本身不存在」**。
因此 W5 加的焦点幂等重试（320 ms × 4）**结构性地不可能生效** —— 它请求的是一个
**还不存在的 `id`**（`.id('callaite_blockEditor_' + uuid)` 没有对应节点）⇒ `focusControl.requestFocus` 必然落空。

### 2.2 缺陷二：权威焦点写入**只单向下行**，不会让目标行进编辑态

`BlockView.onGlobalFocusChanged()`（修复前，`BlockView.ets:1024-1029`）：

```ts
onGlobalFocusChanged(): void {
  if (this.isEditing && this.focusedBlockUuid !== this.blockUuid) {
    this.isEditing = false;      // ← 只做「退出」
    this.refreshBlock();
  }
}                                 // ← 没有「进入」分支
```

`isEditing` 的**唯一**置 true 入口是 `BlockView.enterEdit()`（第 917 行），而它只被**点击类**回调调用
（第 539 / 621 / 713 行）。⇒ 凡「由代码写权威焦点」来迁移焦点的路径都进不了编辑态。

**这一条同时解释了 W5 观测到的另一个现象**：回车后
`AceFocus: RichEditor onBlurInternal` → `FocusSwitch end, RichEditor onBlur, Row onFocus`
—— 焦点之所以掉到 `Row`，正是因为旧行 `isEditing=false` 把 `RichEditor` **整体卸载**了，
焦点无处可去，于是落到行容器上。**「焦点落到 Row」是症状，不是原因** ✓。

**改这一条的语义安全性（已核实，非推测）** Ⓑ：`setFocusedBlock()` 全仓 **14 处**调用点
（`BlockEditor` 7 处：`focusAdjacentBlock`/`routeKeyPreIme`/`routeKeyPostIme`/`routeKeyEnter`×2/建块后权威写入；
`BlockView` 3 处：标记圈点击、行点击、`enterEdit`；`WebEditor` 3 处；定义 1 处）
**全部是「让这个块进入编辑」的意图** —— 没有任何一处是「只高亮不编辑」。
唯一的例外是多选模式（那时点击行**刻意不进编辑**，见 `enterEdit()` 开头），故修复**照抄同一道闸**。

## 3. 修复（最小改动 + 为什么这样改）

### 3.1 `EditorService.ets` —— 补上「结构已变」的视图通知

`entry/src/main/ets/services/EditorService.ets`

| 位置 | 改动 |
|---|---|
| `:5` | `+ import { AppState } from '../state/AppState';` |
| `:240-241` | `createBlockBelow()` **页面末尾**分支：`+ AppState.bumpBlocksVersion();` |
| `:259-263` | `createBlockBelow()` **同级右侧**分支：`+ AppState.bumpBlocksVersion();` |
| `:290-296` | `createChildBlock()` 分支：`+ AppState.bumpBlocksVersion();`（同类缺陷，见 §8）|

**为什么放在 `createBlockBelow` 而不是 `OutlinerEngine.execute()`**：
把 bump 放进引擎会改变**所有** op 的语义（全仓引擎调用点极多），风险面不可控；
而 `createBlockBelow` 是一个**明确的「结构已变且必须让用户看见」的入口**，
与既有的 `BlockView` / `BlockSelection` / `BlockDragLayer` 在自身结构操作后 bump 的做法**同构**。
⇒ 改动面 = 1 个方法 2 个分支，**零语义漂移**（只是补上调用方本就该做的那一步）。

```ts
if (result.success && result.affectedUuids.length > 0) {
  this.focusedBlockUuid = result.affectedUuids[0];
  // ★ W6：同上一分支。`OutlinerEngine` **刻意不 bump** `callaite_blocksVersion`
  //    （全仓仅 UI 组件负责 bump），而它正是 `BlockList` 重算 `rows` 的唯一入口
  AppState.bumpBlocksVersion();
  return this.focusedBlockUuid;
}
```

### 3.2 `BlockView.ets` —— 焦点 `@Watch` 由「只退出」补成「双向」

`entry/src/main/ets/components/outliner/BlockView.ets:1046-1058`

```ts
onGlobalFocusChanged(): void {
  if (this.focusedBlockUuid === this.blockUuid) {
    // W6：权威焦点落到本块 ⇒ 本块进编辑态（多选模式下让位，与 enterEdit 同一道闸）
    if (!this.isEditing && !this.selectionMode) {
      this.isEditing = true;
    }
    return;
  }
  if (this.isEditing) {
    this.isEditing = false;
    this.refreshBlock();
  }
}
```

**为什么必须两条都改**：只改 §3.1 ⇒ 行会被创建，但 `isEditing` 仍是 false ⇒ 仍是只读渲染分支；
只改 §3.2 ⇒ 新行的 `BlockView` 根本不存在 ⇒ `@Watch` 不会被调用到它身上。**二者缺一不可。**

**刻意不做的三件事（红线）** ✗：
1. **不反向写 `setFocusedBlock`**（否则形成「焦点回调 → 写焦点 → 焦点回调」回环）；
2. **不动 `routeKeyEnter` 里「推到下一帧」的权威写入**（W5 用代价换来的：同步写会在同一按键事件内
   销毁本行编辑器 ⇒ `aboutToDisappear` 读到空文本 ⇒ 抹掉本块内容，实测 4664 → 4653）；
3. **不动 `OutlinerEngine`**、不动 `BlockList` / `BlockChildren` 的渲染结构、不动落盘链路。

## 5. Shift+Tab 通道探索结果 ✓（**推翻了 W4/W5 的结论** ✗）

### 5.1 结论

| 通道 | 结论 |
|---|---|
| `uitest uiInput keyEvent <单键码>` | 可用，但**不是唯一形态** —— W4/W5 只用了这一种 |
| **`uitest uiInput keyEvent <keyID_0> <keyID_1> [keyID_2] [displayId]`** | ✅ **真的存在**（`uitest uiInput help` 原文列出），可一次给多个键码；`uitest uiInput keyEvent 2047 2049` 返回 **`No Error`** |
| **`uinput -K -d <key> -u <key> [-i <ms>]`** | ✅ **更好的通道**：`-d`/`-u` 可**重复**，因而能表达「按住 Shift → 敲 Tab → 松开 Shift」这一真实修饰键序列 |

### 5.3 实测可用的命令（Ⓐ 设备实测，返回明确回执）

```bash
# 通道 A：uitest 多键码形态（一次给两个键码）

# 通道 B：uinput —— 真正的「Shift 按下 → Tab 敲击 → Shift 抬起」

#   => you raised the key 2049 / you raised the key 2047     （= 按下与抬起都被接受）

```

**两条实现细节（实测踩出来的）** ✗：
1. **键码必须是十进制**：`uinput -K -d KEYCODE_TAB` / `-d TAB` ⇒ `invalid command to down key`；
   `-d 2049` ⇒ `you raised the key 2049` ✓。
2. **`-d` 与 `-u` 必须交替成对写**：`uinput -K -d 2047 2049 -u 2049 2047`
   ⇒ `please press the 2049 key first` ✗（它不把空格后的数字当作第二个 `-d` 的参数）。
