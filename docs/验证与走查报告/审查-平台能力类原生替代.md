**三条直接推论**

1. **Picker / 剪贴板 / RDB / Preferences / KVStore / WorkScheduler / 通知 / i18n / Asset 在模拟器（OH 画像）上就可用** —— 这些是本轮最值得先做的路线，不需要真机、不需要账号。
2. **OCR / 语音 / 系统分享面板 / 应用内更新 / 云开发（CloudFoundation）/ 华为账号（AccountKit）/ IAP / PDFKit 只在 `*-hmos.json`** —— 模拟器上必然不可用，必须真机 + 华为账号/AGC。项目已有一处实证：`S0-Spike报告.md:109` 记录 `PDFKIT_SYSCAP=false`、`PDFKIT_CTRL_ERR=... does not provide an export name 'pdfViewManager'`。
3. **`@kit.IntelligentCloudKit` 在本机 SDK 中不存在**（OH/HMS 的 `kits\` 目录均无此文件，全盘搜索 `*IntelligentCloud*` 无结果）。任务描述中对该 kit 的预期需要修正；其能力（云端大模型/端云协同推理）在本 SDK 内的对应物是 `@kit.CloudFoundationKit`（云函数/云数据库/云存储）与 `@kit.DataAugmentationKit`（RAG/检索/本地小模型，`@since 6.0.0(20)`，仅 HMOS-2in1 画像声明 `DataAugmentation.RAG`）。

## 2. 推荐前 3 项

> 排序依据：① 是否把「占位/toast 假功能」变成真功能；② 是否可在**当前模拟器**上闭环验证（不需要真机/账号）；③ 迁移成本与风险。

### 🥇 第 1 项 — 接入系统文件选择器 `DocumentViewPicker`（A1 + A2 + A3 合并推进）

**为什么是第一**：这是本域唯一「一处投入、三处假功能同时转正」的路线。

- `PdfPage.ets:44-49` 的 toast「请将 .pdf 放入知识库目录后点击刷新」是**写进代码注释的自我承认**（`:44`：「项目当前未接入系统文件选择器（picker）能力」）；
- `ImportDialog.ets:96` 与 `ExportDialog.ets:159` 让用户**手抄 Linux 沙箱绝对路径**——在真机上用户根本不可能知道 `/data/storage/el2/base/files/graph/...`；
- 三条路线共用同一套 API（`select` / `save`），一次封装成 `PickerService` 即可三处复用。

**关键有利条件（已在本机 SDK 核验）**：
- `syscap SystemCapability.FileManagement.UserFileService`（主）与 `.FolderSelection`（目录）在 **OH-default / OH-tablet / OH-2in1 / HMOS 三画像全部为 Y** → **syscap 层面在模拟器即成立，不需要真机、不需要华为账号**（picker 的 UI 是否在模拟器镜像中完整提供，需实测一次；即便模拟器不提供，真机上一定可用，因为这是全画像 syscap）；
- `@ohos.file.picker.d.ts` **全文件无 `@permission` 声明** → 不需要在 `module.json5` 加任何权限、不需要运行时授权弹窗；
- `@since 9`（`select`/`save` 都是），远低于项目基线 API 24，**无兼容性风险**；
- `@ohos.file.fs.d.ts:2584` 明确「This API returns the result synchronously. This API supports the use of a URI.」→ picker 返回的 URI 可直接进 `fs.openSync/readTextSync`，无需先转路径。

**迁移成本**：低。新增 1 个 `PickerService`（~120 行）+ 改 3 个调用点（合计 ~100 行）。`ImportService`/`ExportService` 的签名从「收路径」改为「收 URI」，内部基本不变。

**必须在真机验证的项**：
1. `.pdf` 的 picker URI 交给 `PdfViewer`（当前是 ArkWeb + pdf.js，`PROJ/ets/components/extensions/PdfViewer.ets`）是否能读到内容——**沙箱外 URI 的读取权限**是本路线唯一实质风险；
2. `DocumentViewPicker.save()` 返回 URI 后，**覆盖已有同名文件**（TRUNC）是否被系统允许；
3. 进程被杀重启后，先前 picker 授权是否失效（决定是否需要「拷贝入沙箱」而非「就地编辑」）；
4. 手机与 2in1 上 `fileSuffixFilters` / `maxSelectNumber` 的 UI 差异。

### 🥈 第 2 项 — 补齐出向分享 `systemShare.ShareController`（B2）

**为什么是第二**：项目当前**分享能力是单向的**——能接收别的应用分享进来的文本/URL（`ShareReceiveAbility`），却**无法把自己分享出去**（全项目对 `systemShare`/`ShareKit` 的 grep 只命中一个方法名）。对一个知识管理应用，「把这一页分享给别人 / 分享到聊天」是高频且用户默认存在的能力，缺失会被直接感知为「不完整」。

**关键 SDK 事实**：

- `@since 4.1.0(11)`，低于项目基线；

**迁移成本**：中。`canIUse('SystemCapability.Collaboration.SystemShare')` 门控 + 不可用时回退到现有 pasteboard 复制路径（B3 已有 4 处可复用），风险可控。

**必须在真机验证的项**：
1. `canIUse('SystemCapability.Collaboration.SystemShare')` 返回 true；

## 3. 不适用项（及理由）

### 3.1 索引层不应落到 RDB（F1）— **不适用**

**理由（三条，均为产品/架构约束而非技术能力约束）**：

1. **`.md` 纯文件是产品的核心承诺，不是实现细节。** `AGENTS.md` 与 `PROJ/ets/core/persistence/FileRepository.ets:1-10` 都明确「纯 Markdown 文件 + 内存索引」；`DataStore.ets:321-331 savePage()` 的唯一落盘动作是 `MarkdownExporter.export()` → 写 `.md`。RDB 一旦成为第二真相源，就必须回答「谁赢」——而当前 `saveAll()` 是**全量逐页重写**（`DataStore.ets:336-341`），任何双写方案都会在强杀/并发下产生不一致。项目已经因为「写入路径不清」踩过两次实证事故（`DataStore.ets:72-83` 空文件被静默跳过、`:140-154` 整页重建把页面清空），再引入第二存储层是放大同类风险。
2. **RDB 的收益在当前数据规模下不成立。** RDB 的价值在「大数据量 + 复杂查询 + 事务 + 并发」。当前索引是 5 个内存 `Map`（`IndexStore.ets:16-28`），查询是 `startsWith`/`indexOf` 前缀匹配（`:137-152`）与三级 property 索引。这些操作在数百到数千页面量级下，内存 Map 的延迟低于任何磁盘 RDB。真正会痛的场景是「万页级 + 全文检索」——那时正确解是 **RDB 的 FTS（全文检索）扩展**或 `@kit.DataAugmentationKit` 的 `retrieval`（向量检索，`syscap DataAugmentation.RAG`，**仅 HMOS-2in1**），而不是把现有索引整体搬进 RDB。
3. **迁移收益与成本严重不对等。** 采用 RDB 需要重写 `IndexStore` + `DataStore` + 全部 `query/*` 组件与 LQL 执行器（`PROJ/ets/core/db/QueryEngine.ets`、`LQLExecutor`），并新增「文件↔DB 同步」这一整层——换来的是当前用不上的事务与并发。

**结论**：保持自研。**但 F2（preferences）与 F3（AssetStore）不在此豁免范围内，应做。**

---

### 3.2 `@kit.AccessibilityKit` 不用于 Tooltip（J3）— **不适用**

该 kit 导出 `accessibility`、`AccessibilityExtensionAbility`、`AccessibilityElement`、`GesturePath` 等，面向**开发读屏/辅助服务类应用**（即「你的应用去操控别的应用」），不是「给自己的组件加 Tooltip / 加无障碍标签」。正解是 ArkUI 通用属性 `bindTips` + `accessibilityText/Role/Group/Level`（见 J2）。

---

### 3.3 `@kit.ArkGraphics2D` 替换自绘画布（G3）— **不适用**

`drawing` / `text` / `effectKit` 的 `syscap` 是 `Graphic.Graphic2D.NativeDrawing`（Native/NAPI 层）。ArkTS 侧要改用需要引入 NAPI 工程与 C++ 侧代码，与项目「无第三方运行时依赖、纯 ArkTS」的既有约束冲突。现有 ArkUI `Canvas` 已满足图谱与白板需求，且白板的手写已经用了官方 `@kit.Penkit` 的 `HandwriteComponent`（`PROJ/ets/components/whiteboard/PenCanvasPage.ets:1`）——这说明团队在「该用原生时用原生」这一点上判断是对的。

---

### 3.4 `@kit.ArkUI` 的 `Share`（任务书表述）— **不存在**

`OH\kits\@kit.ArkUI.d.ts` 全文 grep `Share` **0 命中**（导出的是 `Animator`、`AtomicService*`、各类 `advanced.*` 组件、`window`、`display`、`promptAction` 等）。系统分享的正统入口是 **`@kit.ShareKit`**（HMS）的 `systemShare` / `harmonyShare`，见 B2。任务书中的「`@kit.ArkUI` 的 `Share`」应修正为 `@kit.ShareKit`。

---

### 3.5 `CollaborationService` 用 DistributedKVStore（D4）本身 — **不适用替换**

`syscap DistributedDataManager.KVStore.DistributedKVStore` 在**全部设备画像**（含 OH 模拟器）都有，且这是「跨设备明文键值实时同步」的标准途径。**不该替换**。缺的是它上层的**设备发现与用户授权**（`@kit.DistributedServiceKit` 的 `distributedDeviceManager`，`syscap DistributedHardware.DeviceManager` 全画像有）——当前没有「选择协同设备」的 UI，KVStore 的 `autoSync:true` 完全依赖系统隐式组网，用户无从知道对方是谁、是否连上。

---

### 3.6 `SaveQueue` 用后台任务替换（E1）— **不适用替换，适用补充**

`SaveQueue`（`PROJ/ets/services/SaveQueue.ets:14-70`）解决的是**前台编辑时的强杀丢数据窗口**，1.2s 静默窗口 + `onBackground`/`onSaveState` 双兜底，设计是收敛且正确的。`workScheduler`/`backgroundTaskManager` 解决的是**应用不在前台时**的执行机会，两者**解决的不是同一个问题**。正确做法是保留 `SaveQueue`，另加一个后台任务做「索引重建 / 云同步重试」。
