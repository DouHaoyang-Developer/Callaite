#### P0-1　U1.5 拟删除的 `HomePage.ets` 是**启动默认页**，不是不可达代码

**文档位置**：`PLAN-UI-Alignment.md:141`（表格「HomePage.ets (108L) | **删** | 'Home' 路由不可达」）、
`M1` 出口判据 `:546`。

**事实证据**：

- `AppState.ets:187-189`：
  > 「启动行为调整：不再恢复上次页面/直接加载大纲，统一进入首页（Obsidian 新标签页式）。… 启动初始页固定为 Home。」
  > `AppStorage.setOrCreate(STORAGE_KEYS.currentPage, 'Home');`
- `AppState.ets:227` 历史栈初值用 `?? 'Home'`；`AppState.ets:260` `getCurrentPage()` 兜底 `?? 'Home'`。
- `PageView.ets:142-143`：`} else if (this.page() === 'Home') { HomePage() }` —— **在实时渲染路径上**。

**后果**：`'Home'` 是**冷启动落地页 + 兜底路由**。删掉组件与分支后，首启会落到
`PageView.ets:150-215` 的 `else`（通用页面）分支，渲染一个名为 "Home" 的空页面。
这会让「统一进入首页」这一已有设计直接失效，且属于 M1 的出口判据范围。

**修订**：从 U1.5 表中移除 HomePage。若确实要下线首页，需单独立项（改 `AppState.ets:189` 的启动路由 +
`PageView.ets:142` 分支 + 回退策略），不能混在「死代码清扫」里。

#### P0-2　U1.5 拟删除的 `Toolbar.ets` 是活代码，且方案的验证规程会把它自动还原

**文档位置**：`PLAN-UI-Alignment.md:147`（「Toolbar.ets (68L) | **删** | 撤销/重做已由 MarkdownToolbar（移动）+ Ctrl+Z（桌面）覆盖」）、

**事实证据**：

- `ContentArea.ets:5`：`import { Toolbar } from '../outliner/Toolbar';`

#### P0-4　TabState v2 的 `v: 2` 字段会清空用户标签

**文档位置**：`PLAN-DocumentEditor.md (v1.md:447`（§6.3「持久化 JSON 增加 `v: 2` 字段；解析时无 `snapshot` 的旧格式 → 填默认零值」）。

**事实证据**：

- `TabState.ets:54`：`const parsed = JSON.parse(raw) as TabInfo[];` —— 顶层按**数组**解析。
- `TabState.ets:55`：`if (!parsed || parsed.length === 0) { return []; }`
- `TabState.ets:36-37`：`initialize()` 中 `if (existing.length === 0) { …persist([home], home.id); }`
  （home 是 `{page:'Journal'}`）。

若把 `v` 放在顶层（形如 `{"v":2,"tabs":[…]}` 或 `[…], v:2` 等非数组形态），
`parsed.length` 为 `undefined` → `:55` 判空不成立 → `:59` 的 `for` 循环以 `undefined` 为界**不执行** →
返回 `[]` → `initialize()` 在 `:36` 判定「无标签」→ **写回单个 Journal 标签，用户的全部标签丢失**。
方案未说明 `v` 的落点，且 §6.3 的「兼容」描述只覆盖了 `snapshot` 缺失，没覆盖容器形态变化。

**加剧因素**：`TabState.getTabs():58-65` 是**白名单式逐字段重建**（只拷贝 `id`/`page`/`pinned`），
不是透传。若忘记在 `:63` 补 `snapshot`，快照会**在每次读取时被静默丢弃**，
而 `:58-65`、`:125`、`:162`、`:187` 共 **4 处**必须同步修改，方案未列出这些落点。

**修订**：
- 明确 `v` 的落点（推荐：**保持顶层数组**，把版本放进每个元素或新增一个独立的
  `callaite_tabsSchemaVersion` 键），并写一条「旧格式解析失败 → 不落盘、仅用默认值」的保护。
- 在 §6.1 用一张表列出 `TabState.ets` 的 4 个构造/重建落点。
- §6.3 的「`escape()` 足够」需补注：`escape()`（`:224-226`）只转义 `\` 与 `"`，
  **不处理控制字符**，严格来说不是合法 JSON 转义；`scroll`/`caret` 是数字，必须原样输出而非经 `escape()`。
  这是既有实现的潜在缺口，不是本方案引入的，但本方案明确依赖它，应当记录。

#### P1-2　DocumentEditor 的保存链模型与代码不符，且是性能预算的基准

**文档位置**：`PLAN-DocumentEditor.md (v1.md:106`（I3：「保存链唯一：`edit.block` → `EditorService.updateBlockContent`
→ `SaveQueue`（**400ms 防抖兜底**）→ FileRepository」）、`:155`（「JS 侧 150ms 合并，原生 SaveQueue **400ms** 兜底」）、
`:331`（「冷启动预算…」）、`:588`（§9.2）、`:516`（Phase 2 验收「内容丢失 ≤ autosave 间隔 + **400ms**」）。

**事实证据**：

- `EditorService.updateBlockContent:180-190` 只做一件事：`ws.executeOp({type:'update-block', …})`，
  **没有任何 `SaveQueue` 调用**（`:188` 注释「操作成功后 Engine 内部已触发持久化」）。
- `OutlinerEngine.persistForOp:361-376`：对 `update-block` 等 14 种 op **同步**调用
  `this.dataStore.savePage(pageId)`。
- `DataStore.savePage:321-331`：`MarkdownExporter.export(page, blocks)` 导出**整页** markdown →
  `fileRepo.writeTextSync(fullPath, markdown)`。
- `FileRepository.writeTextSync:127-140`：临时文件 + `fs.fsyncSync(file.fd)` + `fs.renameSync`
  —— **同步阻塞式整页落盘，含一次 fsync 系统调用**。
- `SaveQueue.ets:22`：`QUIET_MS = 1200`（**1.2 秒，不是 400 毫秒**）；
  且 `:43-52` 的 `markDirty()` 在 `timerId >= 0` 时直接返回（**窗口不随新变更顺延，这是节流不是防抖**）。
  `SaveQueue` 是**整图脏标记**路径，不在 `update-block` 的链路上。

**后果（双向都错）**：

1. **性能**：方案预期「150ms 合并 + 400ms 防抖」的温和节流；真实的代码路径是
   **每 ~150ms 一次整页 markdown 导出 + 临时文件写 + fsync + rename，全部同步，在主线程**。
   方案 §9.2 的性能预算表（`:586-593`）里「键盘敲击 → 屏显 < 30ms」「滚动 1000 块 >55fps」
   都没有为这条路径留预算；而 fsync 阻塞正是本项目已知的 THREAD_BLOCK/appfreeze 类问题的成因类别。
2. **数据安全**：真实持久化比方案以为的更即时（几乎每 op 落盘），所以「kill 后丢失 ≤ 400ms」的
   验收判据虽然数字错，但结论方向偏保守，不算危险——**危险的是它掩盖了主线程 fsync 这一项**。

**修订**：
- §2.2 I3 改写为真实链路，并把「`edit.block` 是否应经 SaveQueue 而非 `persistForOp`」列为
  **Phase 2 的架构决策项**（这是本方案唯一需要动原生持久化层的地方，方案漏了）。
- §9.2 增加「500 块页面连续输入 10s，主线程无 >100ms 卡顿」预算 + Profiler 测量方式。
- 全文 `400ms` 改为 `1200ms`（`:106`、`:155`、`:516`），或明确改为「方案将 SaveQueue 窗口调至 400ms」
  并把它列入 Phase 2 改动清单。

   `caret.change` 接到 `setFocusedBlock`，需先确认这类既有不对称是否会引发焦点态分裂。**存疑**。
6. **U2.3 中「`ShortcutSettings` 页同步（它是读注册表的，自动跟随）」**：已核实
   `ShortcutSettings.ets:72` 确读 `ShortcutService` 的 `defs`，此项判断**成立**；

   全仓无调用点，故不可达 ✓。但**未验证**是否存在运行期通过字符串/路由表间接进入的路径

   故判定成立。此条已澄清，列此仅为留痕。
8. **`UpdateBlockOp` 的 undo 支持**：`OutlinerEngine.ets:329`
   `return { success: false, message: 'Undo content update not supported', affectedUuids: [] };`
   —— 即**结构栈的 undo 不支持文本更新**。DocumentEditor §4.10 把文本撤销放在 JS 自维护栈
   （「JS 栈顶属于当前块 → 本地应用；否则发 `op.request: undo`」）。这意味着
   **「块内打字 → 切到另一块 → Ctrl+Z」会退化为「Update content 不支持撤销」**，
   路由规则（`:349`）无法兜住跨块的文本撤销。方案把它归为「两栈不互通，v1 接受」，
   但实际表现比「不互通」更差（撤销可能完全无效并静默失败）。**存疑**：建议 Phase 2 明确
   `update-block` 的 undo 行为并纳入验收。
