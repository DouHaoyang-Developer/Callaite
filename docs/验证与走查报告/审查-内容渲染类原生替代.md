# 审查：内容渲染与文档处理 —— 原生替代可行性

- **审查域**：内容渲染与文档处理（Markdown 渲染 / 代码高亮 / 公式 / 图表 / 编辑器 / PDF / 图片附件 / 导入导出）
- **被审项目**：`F:\DevEcoStudioProjects\Callaite`（ArkTS/ArkUI，`entry/src/main/ets` 145 个 `.ets`）
- **SDK**：
  - OpenHarmony 基础：`D:\Program Files\Huawei\DevEco Studio\sdk\default\openharmony\ets`
  - HMS 扩展：`D:\Program Files\Huawei\DevEco Studio\sdk\default\hms\ets`
- **项目 SDK 配置（已核验）**：`Callaite\build-profile.json5` → `targetSdkVersion: "26.0.0"` / `compatibleSdkVersion: "26.0.0"`；`Callaite\entry\src\main\module.json5` → `deviceTypes: ["phone","tablet","2in1"]`
- **第三方依赖（已核验）**：`Callaite\oh-package.json5` → `dependencies: {}`、`Callaite\entry\oh-package.json5` → `dependencies: {}`。**项目零第三方运行时依赖；所有「第三方库」均为 WebView 运行时从 CDN 拉取。**
- **铁律**：本报告所有「原生替代」均只给出**类型面**证据（d.ts 路径 + 行号 + syscap + since + 设备档案）。类型面 ⊃ 运行时能力面，每条路线都附「真机验证项」，`@hms.*` 路线必须先 `canIUse('<syscap>')`。
- **核验范围声明**：本报告只写入**已核验**的事实（d.ts 存在性与声明行、项目代码位置）。无法从类型定义判定的写入第 4 节「不确定项」并标「存疑」。

## 2. 推荐替代的前 3 项

### 推荐 1：PDF 阅读与标注 → 原生 `PdfView` + `PdfController`（真机路线，模拟器保留 pdf.js 回退）

**理由（全部有据）**
1. **接入面完全覆盖现状**：当前 `PdfViewer.ets` 提供的能力（上一页/下一页、文本选中、高亮、持久化、翻页计数）在 PDF Kit 里均有对应声明——`loadDocument`（`PdfView.d.ets:798`）、`registerTextSelectedListener`（`:1169`，带回 `TextSelectedParam{text, pdfRect}` `:442-459`）、`enableAnnotation`（`:1057`）、`addMarkupAnnotation`（`:1071`）、`registerAnnotationChangedListener`（`:1210`）、`saveDocument`（`:1119`）。
2. **消除一个结构性缺陷**：当前实现把整份 PDF 读成 `ArrayBuffer` → base64 → 拼进 HTML（`PdfViewer.ets:105-117`、`:164`），内存与字符串开销随文件线性增长；`loadDocumentFromMemory(ArrayBuffer)`（`:1374`）可直接吃 `ArrayBuffer`，甚至可直接 `loadDocument(path)`（`:798`）传沙箱路径。
3. **顺带拿到现在没有的能力**：全文搜索 `searchKey`（`:1232`）+ `setSearchIndex`（`:1259`）、缩放 `setPageZoom/setMinZoom/setMaxZoom`（`:843/899/871`）、页面布局 `setPageLayout`（`:919`）、缩略图 `getPagePixelMap`（`:757`）。
4. **设备面已声明支持本项目全部 `deviceTypes`**：`module.json5` = phone/tablet/2in1；`api-version\PDFKit.json:12-28` 给出 phone(12)/tablet(12)/2in1(13)。

**风险**
- **铁律触发点**：syscap 在模拟器为 false（已知事实）。本 SDK 中 `hms\ets\api\device-define\phone.json`（非 `-hmos` 档案，对应 OpenHarmony/模拟器面）grep `PDFService` **零命中**，而 `phone-hmos.json:87` 有 —— 两侧证据一致，**必须 `canIUse()` 双路**：true 走原生，false 走现有 pdf.js。
- **语义冲突**：`saveDocument`（`:1119`）会把标注写进 PDF 本体，而当前实现是旁挂 `<pdf>.highlights.json`（`PdfViewer.ets:119-144`）。二选一需产品决策；建议 v1 只用 `setHighlightRects`（`:821`）/`addMarkupAnnotation` 做**会话内**高亮，不调 `saveDocument`，标注文本仍按现有语义写回 block。
- `loadDocumentFromMemory` since 26.0.0，若目标真机 ROM 低于该 API 版本则运行时可能缺失 —— 回退到 `loadDocument(path)`。

**真机验证项（按顺序）**
1. `canIUse('SystemCapability.OfficeService.PDFService.Core')` === true
2. `new pdfViewManager.PdfController()` 不抛异常（复用 `SpikeHarness.ets:40-54` 已有探针）
3. `PdfView({ controller })` 挂载后 `loadDocument(path)` 成功返回 `ParseResult`
4. `registerTextSelectedListener` 回调在真机触摸选中时触发，`text` 与视觉选段一致
5. `addMarkupAnnotation(SupportedAnnotationType.HIGHLIGHT, selectedRects, 0x80FFEB3B)` 视觉正确
6. 切页 / 缩放 / 横竖屏后 `pdfRect` 坐标系是否需重算

### 推荐 2：新增「导出 PDF」→ ArkWeb `createPdf()` + 复用现有 `ExportService.exportHtml()`

**理由**
1. **填补真实空缺**：`ExportDialog.ets:55-80` 只有 md / html / opml 三种；`ExportService.ets` 无任何 PDF 相关代码（全文件已读）。
2. **零新依赖、复用已有资产**：`ExportService.exportHtml(pageName)`（`ExportService.ets:45-80`）已经生成完整独立 HTML（含内联 `<style>`），可直接 `src` 喂给 `Web`，调 `createPdf()` 拿 `PdfData.pdfArrayBuffer()`（`@ohos.web.webview.d.ts:475`）→ 用 `@kit.CoreFileKit` 的 fd 写入（项目既有的 `openSync(…CREATE|WRITE_ONLY|TRUNC)` + `writeSync(fd, content)` 模式）。
3. **syscap 稳妥**：`SystemCapability.Web.Webview.Core` 在 `default.json:180`/`tablet.json:173`/`2in1.json:140` 均存在（比 PDFService 稳得多）；since 14，远低于项目 `compatibleSdkVersion: 26.0.0`。

**风险**
- `PdfConfiguration` 单位是**英寸**（`@ohos.web.webview.d.ts:494`「Recommended value: 8.27 inches of A4 paper width」），换算错误会导致版面错乱。
- 分页由引擎决定，`page-break-*` CSS 是否被尊重 **存疑**。
- 需一个 `Web` 实例承载（可见或不可见），未验证是否支持完全离屏。

**真机验证项**
1. 中文文本是否正常嵌入（不出现方框/乱码）
2. `width=8.27, height=11.69` 下的实际点阵与页数
3. `<pre>`、`<ul>`、`<blockquote>`（`ExportService.ets:56-71` 的样式）跨页时是否被切断
4. `pdfArrayBuffer()` 长度 > 0 且写入沙箱后系统 PDF 应用可打开
5. 大批量导出（`exportAllHtml` 路径）时的内存释放

### 推荐 3：整页阅读视图（preview / split 预览）→ `StyledString` + `TextController.setStyledString`

**理由**
1. **直击任务书点名的「自研行级 Text 重建」**：现状是 `IntegralEditor.ets:62-100` 手写 `rebuildPreview()`（按 `\n` 切行、判 `#`/`- `/`> ` 前缀、硬编码字号 26/22/19/15/13/11 与缩进 0/12/16）+ `:243-270` 每行一个 `Text` + 一个 `Circle` 圆点。这是**逐行、逐控件**的还原，行高/换行/选中/复制全丢失。
2. **原生能一次承载整页富文本**：`Text` 支持 `TextController`（`component/text.d.ts:1811`）与 `setStyledString`（`:1833`）；`StyledStringValue`（`styled_string.d.ts:1538`）联合类型覆盖 `TextStyle`（`:328`）、`DecorationStyle`（`:664`）、`ParagraphStyle`（`:1041`，段落缩进/对齐）、`LineHeightStyle`（`:1364`）、`LineSpacingStyle`（`:1439`）、`UrlStyle`（`:1492`，since 14，可点击链接）、`ImageAttachment`（`:1905`，行内图片）、`GestureStyle`（`:970`）、`BackgroundColorStyle`（`:927`，since 14，可做行内代码底）。
3. **syscap 面最稳**：`SystemCapability.ArkUI.ArkUI.Full`，在 `default.json:4`、`tablet.json:4`、`2in1.json:220`、`wearable.json:15` 全部存在；主 API since 12，项目 compatible 26.0.0 有充裕余量。
4. **顺带修复一个已知脆弱点**：`IntegralEditor.ets:104-112/151-156/173-178/193-199` 那一串「RichEditor 重建 → extractText 为空 → 整页被清空」的防御代码，源于把「渲染」与「编辑」压在同一个 `RichEditor` 实例上；把 preview/split 的渲染层换成 `Text + StyledString`（只读）可以从结构上消除该风险类。

**风险**
- `StyledString` 是**扁平字符流 + 区间样式**，没有块模型：任务清单、表格、Mermaid、公式仍需现有组件兜底（`BlockView.ets:139-149` 的 `TableView`、`:293-294` 的 MermaidRenderer）。
- `UrlStyle` 是否可点击、`GestureStyle` 命中区是否精确 —— d.ts 只有 `constructor(url)` 与 `readonly url`（`:1503/1513`），**存疑**。
- 需要把 `MarkdownExporter` 的输出（Markdown）在 ArkTS 侧转成 `MutableStyledString`，这是新的自研解析层（但比「逐行 Text 重建」更薄、更可测）。

**真机验证项**
1. 单 `Text` 承载 5k+ 字 + 200 段样式时的首帧与滚动帧率
2. `ParagraphStyle.leadingMargin`（配合 `LeadingMarginPlaceholder` `rich_editor.d.ts:449`）能否做出 `IntegralEditor.ets:88-90` 的列表缩进
3. `ImageAttachment`（`styled_string.d.ts:1905`）的加载与高度自适应
4. `GestureStyle` 对 `[[页面引用]]` / `#标签` 的点击命中与 `BlockView.ets:305/332` 的一致性
5. `UrlStyle` 是否触发系统链接跳转（对比 `ContentRenderer.ets:315-324` 现有 `ctx.openLink`）

## 5. 结论速览

- **可推荐替代**：R1/R2/R3（`StyledString` 阅读视图）、R9（PDF Kit）、R11（`createPdf` 导出）、R13（Image Kit 缩略图）、R14（`DocumentViewPicker`）、R12（CDN→rawfile 治理）。
- **能力上不可替代、必须保留第三方**：语法高亮 token 着色、KaTeX 公式、Mermaid 图表；Markdown 解析三件套（`ContentRenderer` / `ImportService` / `ExportService`）也应保留。
- **架构判断**：「块级 `WebEditor` → 文档级 `WebView + CodeMirror`」的动机（`PLAN-DocumentEditor.md` ADR-003：焦点迁移生命周期 churn、每块 `.height(32)` 结构性裁切）**成立**；但**「因为原生 RichEditor 不行」不成立** —— `RichEditor` 的能力面（`addBuilderSpan` / `editMenuOptions` / `bindSelectionMenu` / `customKeyboard` / `StyledString` 控制器）远超当前用法，现有缺陷主要来自 `IntegralEditor` 的用法（同实例承载渲染与编辑、重建无回填）。建议先做 R5 的最小修复 spike，再决定是否整体 WebView 化。
